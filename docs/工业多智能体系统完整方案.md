# 工业多智能体系统完整方案
## WMS / MES / QMS 事件驱动 + LangChain / LangGraph 协同 + 知识库决策 + 受控执行

> 技术栈：Python + uv 包管理 | LangChain 能力底座 + LangGraph 多智能体编排 + 自研工业工具层
> 文档版本：v1.0 | 整理日期：2026-11-26

---

## 1. 方案目标

构建一个面向工业现场的多智能体协同系统，接入 WMS、MES、QMS、设备系统、知识库等业务与数据源，实现以下能力：

1. 自动接收生产、物料、质量、设备等异常事件
2. 自动调用多个专业智能体进行协同分析
3. 结合设备信息、业务数据和知识库生成解决方案
4. 根据风险等级决定自动处理、生成提示、创建工单草稿或转人工确认
5. 全过程可追溯、可审计、可回放、可回滚
6. 不绕过现有 WMS / MES / QMS 业务规则，不直接让大模型控制设备

系统的核心定位是：

> AI 智能体负责事件理解、信息检索、协同分析、方案生成、风险提示和低风险受控处理；高风险动作仍由业务系统、权限体系和人工确认共同约束。

### 架构选型总纲

```text
LangChain（智能体能力底座）+ LangGraph（多智能体流程编排）+ 自研工业工具层（确定性执行边界）
```

- LLM 负责理解和规划，工具层负责确定性执行，LangGraph 负责流程、分支、重试、审计和人工确认。
- 不要让 LLM 直接操作工业系统：所有工业动作必须封装成工具，由工具层做权限、参数校验、超时、审计和失败处理。

## 3. 技术选型建议

| 层级 | 推荐技术 | 作用 |
|---|---|---|
| 智能体能力层 | LangChain | 模型调用、工具封装、RAG、结构化输出 |
| 多智能体编排层 | LangGraph | 主调度、子图、条件路由、人工确认节点 |
| 事件接入层 | Kafka / RabbitMQ / Redis Stream / Pulsar | 接收 WMS、MES、QMS 等系统事件 |
| 工具适配层 | 自研 Adapter | 对接设备、数据库、WMS、MES、QMS、知识库 |
| 数据存储层 | PostgreSQL / 时序库 / 对象存储 | 业务数据、审计数据、文档、模型输入输出记录 |
| 知识库层 | 向量库 + 元数据库 | SOP、故障案例、维护记录、工艺规范检索 |
| 治理层 | 自研权限、审计、风险策略模块 | 控制高风险动作，保证安全边界 |

消息中间件选型不强制绑定某一种，应根据现有基础设施、吞吐要求、延迟要求、运维能力选择。高频设备告警场景更关注低延迟和流式处理；业务系统集成更关注可靠投递、幂等、死信和回放。

## 4. 事件驱动设计

### 4.1 事件来源

| 系统 | 典型事件 | 触发场景 |
|---|---|---|
| WMS | 缺料、库存不足、批次冻结、发料失败、库位异常 | 物料无法支撑生产或库存状态异常 |
| MES | 工单阻塞、工序异常、报工异常、停线、在制品异常 | 生产执行过程出现偏差 |
| QMS | 来料不合格、过程不良、终检异常、CAPA 触发 | 质量异常需要追溯和处置 |
| EAM / 设备系统 | 设备故障、参数越限、通讯中断、维保到期 | 设备状态异常影响生产 |

### 4.2 标准事件格式

所有系统推送给智能体平台的事件应统一格式，字段必须稳定，否则后续 Agent 路由、审计、回放都会混乱。

```json
{
  "event_id": "evt-20261126-000123",
  "event_type": "mes.work_order.blocked",
  "source_system": "MES",
  "occurred_at": "2026-11-26T10:20:00+08:00",
  "received_at": "2026-11-26T10:20:01+08:00",
  "severity": "high",
  "tenant_id": "factory_a",
  "factory_id": "F-01",
  "line_id": "LINE-03",
  "work_order_id": "WO20261126001",
  "material_id": "M-10023",
  "batch_id": "B20261126-08",
  "device_id": "DEVICE-A-001",
  "alarm_code": null,
  "message": "工序阻塞，疑似缺料",
  "trace_id": "trace-8f3a92",
  "idempotency_key": "MES-WO20261126001-OP-20-blocked",
  "payload": {
    "process_id": "OP-20"
  },
  "raw_payload": {},
  "data_quality": "complete",
  "schema_version": "v1"
}
```

> 与 `models/events.py` 的 `StandardEvent` 对齐：工单 / 产线 / 物料 / 批次 / 设备 / 报警码 / 消息等**提升为顶层可选字段**，`payload` 仅保留透传扩展字段，`raw_payload` 保存原始报文，`data_quality` 取值 `complete` / `partial` / `suspicious`；`source_system` 限 `WMS` / `MES` / `QMS` / `EAM` / `MANUAL`，`severity` 限 `low` / `medium` / `high` / `critical`。事件聚合后生成 `Incident`，其 `incident_type`（`production_exception` / `material_exception` / `quality_exception` / `equipment_exception` / `mixed_exception` / `query` / `standalone`）写入状态并驱动主图路由。

### 4.3 事件治理层能力

事件进入 Agent 前，必须经过治理层处理，避免重复分析、告警风暴、成本失控、重复写操作和高风险误触发。

| 能力 | 说明 |
|---|---|
| 去重 | 同一设备、工单、批次重复异常只处理一次 |
| 聚合 | 多个相关报警合并为一个问题 |
| 限流 | 防止告警风暴打爆模型和工具 |
| 优先级 | 停线、批量质量异常、安全风险优先处理 |
| 幂等 | 同一事件重复消费不重复执行 |
| 死信队列 | 处理失败后进入人工兜底 |
| 审计 | 记录事件来源、处理过程、结果 |

## 5. 多智能体架构

### 5.1 主调度 Agent（Supervisor）

主调度 Agent 即 `src/industrial_agent/graph/orchestrator.py` 构建的 LangGraph 主图，不直接查设备、不直接控制设备，只负责任务编排。其路由事实全部来自 `src/industrial_agent/agents/catalog.py`：

- 按事件类型 `incident_type` 确定子图（`INCIDENT_SUBGRAPH`）
- 按路由映射展开为具体智能体编号（`ROUTE_AGENT_MAP`）
- 按第一版范围收敛（`resolve_codes`，`release_scope="first"`）；收敛后若不存在分析主脑（B3 / A3 / B4），统一回落到 **B3 只读诊断**
- 合并多个 Agent 的 `AgentFinding` 结果，判断证据是否充分
- 调用 `planning/builder.py` 的 `PlanBuilder` / `RiskClassifier` 生成方案并分级
- 按 `config.py` 的灰度策略分流：自动执行 / LangGraph `interrupt` 中断等待人工确认

### 5.2 专业子 Agent（13 类智能体目录）

> 代码已不再使用早期文档的“7 个通用 Agent”划分，统一采用《智能体构建清单方案》定义的 **13 类智能体**（A1–A5 / B1–B5 / C1–C3），唯一事实来源为 `src/industrial_agent/agents/catalog.py` 的 `AGENT_CATALOG`。13 类智能体的编号、名称（代码标识符）、子图、确认边界、风险上限、第一版范围、输入 / 工具 / 知识库对齐，见《智能体构建清单方案》“六、与代码实现的精确对齐”。

实现要点：

- 所有专业子 Agent 继承 `agents/base.py` 的 `BaseAgent`，对外统一输出 `models/findings.py` 的 `AgentFinding`，字段包括 `summary` / `findings` / `hypotheses` / `evidence` / `confidence` / `data_gaps` / `suggested_next_steps` / `risk_notes` / `knowledge_refs`。
- `BaseAgent._call` 通过 `tools/registry.py` 的 `ToolRegistry` 调用工具，写动作受 `confirm_boundary`、工具风险等级与灰度策略约束；第一版只读智能体（A1 / B1）的写工具会被前置检查拦截（`WRITE_BLOCKED`）。
- `BaseAgent._llm_finding` 为可选 LLM 结构化输出（`agents/llm.py`），LLM 未配置或输出校验失败时自动降级为规则取证结果，保证“规则优先 + LLM 可选降级”。
- C1–C3 行业专用智能体由 `agents/industry.py` 的 `IndustryRulePack` 承载，经 `IndustryRuleAgent` 确定性发射校验项与确认边界，**不调用工具、不自由协作**，按子图注入（`INDUSTRY_INJECTION`）。

### 5.3 编排模式（已落地 Supervisor 主调度）

代码已采用 **Supervisor 主调度模式**：单张 LangGraph 主图内按路由分发到具体智能体并顺序调用，而非早期设想的“每个 Agent 一个独立子图”。主图统一维护 `graph/state.py` 的 `IndustrialAgentState`，子 Agent 只接收 `AgentContext`（事件 + 知识命中 + 工具入口 + 审计）并返回 `AgentFinding`，保证确定性、可追溯性与可测试性。

实际路由分发如下（前为分析主脑，后为协同取证，括号内为按子图注入的行业规则）：

```text
主调度图（orchestrator.py）
  |-- equipment_exception:  B3 -> A1 -> A3          （+ C1）
  |-- quality_exception:    A3 -> B4 -> B3          （+ C1 / C2）
  |-- material_exception:   A2 -> B2 -> A4 -> A1    （+ C3）
  |-- production_exception: A4 -> A2 -> B2 -> A1    （+ C3）
  |-- query:                B1 -> A1                （+ C2 / C3）
  |-- standalone:           A5 -> B5                （独立链路，不入异常主链）
  -- mixed_exception:       B3 -> A2 -> B2 -> A4 -> A3 -> A1  （+ C3）
```

不采用完全自由协作的 Swarm 模式：工业系统重视确定性、可追溯性、权限边界和审计能力，主调度模式更稳。层级子调度模式（按运维 / 质量 / 生产运营 / 物料供应拆分）留待系统规模扩大后评估。

## 6. 统一工具层设计

所有 Agent 必须通过统一工具层访问设备和业务系统，不允许每个 Agent 自己直连数据库、设备或控制接口（否则权限、审计、参数校验都会不一致）。

```text
所有 Agent -> 统一工具层 -> 统一适配器 -> 工业系统 / 设备 / 数据库 / 知识库
```

### 6.1 工具分类（与 `tools/contracts.py` 对齐）

代码用两个正交维度描述工具：`kind`（`read` / `write` / `control`）与 `risk`（`low` / `medium` / `high`）。`tools/factory.py` 默认装配 **17 个工具**：

| 工具名 | kind | risk | 说明 | 第一版可用性 |
|---|---|---|---|---|
| query_device_status | read | low | 查询设备实时状态 | 可用 |
| query_recent_alarms | read | low | 查询设备最近报警 | 可用 |
| query_device_trend | read | low | 查询设备测点趋势 | 可用 |
| query_work_order | read | low | 查询工单状态 / 工序 / 数量 | 可用 |
| query_material_stock | read | low | 查询物料可用量 / 在途 / 安全库存 | 可用 |
| query_batch | read | low | 查询批次冻结状态与库位 | 可用 |
| query_quality_record | read | low | 查询检验结果 / 不良代码 / 追溯链 | 可用 |
| load_esop | write | medium | 加载 E-SOP（A1 / B1，记录态） | A1/B1 只读时被拦截 |
| bind_codes | write | medium | 码批绑定生成装配履历（A1 / B1） | A1/B1 只读时被拦截 |
| create_dispatch_suggestion | write | medium | 生成调度建议草稿（A4） | 不在第一版（A4 未启用） |
| reuse_process_template | read | low | 复用工艺模板（C3） | 不在第一版 |
| training_score | read | low | 实训评分与画像（A5 / B5） | 不在第一版 |
| create_ticket_draft | write | medium | 创建工单草稿 | 可用 |
| send_notification | write | medium | 发送通知给责任人 | 可用 |
| adjust_delivery_route | control | high | 配送路径调整（仅生成建议） | 须人工确认 |
| control_device | control | high | 设备停机 / 启机 / 参数修改 | 须人工确认 |
| freeze_batch | control | high | 冻结批次 | 须人工确认 |

`ToolSpec.auto_executable` 的判定规则：`risk != "high"` 即可自动执行；高风险工具一律需人工确认。

### 6.2 工具层统一处理（与 `tools/registry.py` 的 `ToolRegistry` 对齐）

`ToolRegistry` 是所有智能体访问外部系统的唯一入口，`invoke` 的前置检查链**顺序固定**，任意一环失败即返回 `ToolResult(ok=False)` 并落审计：

1. **存在性检查**：工具未注册 → `TOOL_NOT_FOUND`
2. **权限检查**：调用者角色不满足 `required_roles` → `PERMISSION_DENIED`
3. **高风险拦截**：`risk == "high"` 且 `context.allow_high_risk` 为假 → `HIGH_RISK_BLOCKED`（高风险动作必须先经人工确认置位）
4. **写动作拦截**：`kind in (write, control)` 且 `context.allow_write` 为假 → `WRITE_BLOCKED`（用于 A1 / B1 只读取证与影子模式）
5. **幂等检查**：写 / 控制类工具带 `idempotency_key` 时命中缓存直接返回
6. **审计落盘（调用前）**：记录 `action=tool:{name}`、`decision=allowed`
7. **执行**：`read` 且 `retryable` 时重试 1 次；超过 `timeout_seconds` → `TOOL_TIMEOUT`；参数 `TypeError` → `INVALID_ARGS`；无数据 → `NO_DATA`（`degraded=True`）；下游异常 → `DOWNSTREAM_UNAVAILABLE`
8. **审计落盘（调用后）**：记录 `action=tool:{name}:result`、`decision=executed/denied`
9. 写 / 控制类成功后写入幂等缓存

`ToolContext` 关键字段：`trace_id`（链路追踪）、`incident_id`、`actor`、`roles`、`tenant_id`、`allow_high_risk`、`allow_write`。`ToolResult` 统一返回：`ok` / `data` / `error_code` / `error_message` / `source` / `fetched_at` / `degraded`。

### 6.3 工具封装示例（与实际 `ToolSpec` 对齐）

代码不使用 langchain 的 `@tool` 装饰器，而是用 `ToolSpec` 数据类 + 可调用 `handler` 注册到 `ToolRegistry`：

```python
from industrial_agent.tools.contracts import ToolContext, ToolSpec
from industrial_agent.tools.registry import ToolRegistry

spec = ToolSpec(
    name="query_device_status",
    description="查询设备实时状态：运行状态、关键测点、采集时间、数据质量",
    kind="read",
    risk="low",
    timeout_seconds=5.0,
    handler=query_device_status_handler,  # 真实项目对接 Modbus / MQTT / OPC UA / 数据库适配器
)

registry = ToolRegistry()
registry.register(spec)

result = registry.invoke(
    "query_device_status",
    {"device_id": "DEVICE_TYPE_A-01"},
    context=ToolContext(trace_id="t-001", incident_id="inc-001"),
)
# result.ok / result.data / result.error_code
```

高风险工具（`control_device` / `freeze_batch` / `adjust_delivery_route`）的 `handler` 只有在 `context.allow_high_risk=True` 时才会被调用；该标志由执行节点在人工确认通过后置位，未经确认的高风险调用在前置检查第 3 步即被拦截。

## 7. 知识库与设备信息融合

### 7.1 设备信息作用（回答“当前发生了什么”）

设备实时状态、测点数据、报警记录、历史趋势、运行参数、维保记录、故障历史、通讯状态。

### 7.2 知识库作用（回答“标准上应该怎么处理”）

SOP、工艺规范、故障处理手册、历史案例、安全注意事项、质量处置规则、维护流程、设备说明书。

### 7.3 检索推荐逻辑

```text
设备编号 + 报警代码 + 设备类型 + 异常关键词
  -> 检索 SOP
  -> 检索历史故障案例
  -> 检索维护记录
  -> 检索安全注意事项
  -> 生成候选方案
```

检索维度建议覆盖：设备编号、设备类型、报警代码、异常关键词、工单类型、物料类型、质量不良代码、时间范围。

检索建议区分数据类型：

- SOP、工艺规范、维修案例：适合 RAG
- 设备实时状态：必须走工具查询，不要让 LLM 猜
- 追溯数据：必须走数据库或业务系统接口
- 控制参数：必须有规则校验，不能只依赖模型输出

### 7.4 知识文档必须带元数据（与 `models/knowledge.py` 的 `KnowledgeChunk` 对齐）

```json
{
  "chunk_id": "kc-001",
  "doc_id": "SOP-EQ-001",
  "title": "主轴温度异常处置规程",
  "section_path": "第3章 温升异常/3.1 排查步骤",

  "applicable_device_types": ["CNC", "MACHINE_CENTER"],
  "applicable_alarm_codes": ["TEMP_HIGH", "SPINDLE_OVERHEAT"],
  "applicable_process": ["OP-10", "OP-20"],
  "applicable_product_codes": [],
  "risk_level": "high",
  "owner": "设备工程部",
  "text": "......",
  "source_uri": "kb://SOP-EQ-001#第3章 温升异常/3.1 排查步骤"
```

关键实现约束（对齐 `knowledge/store.py` 的 `KnowledgeStore.retrieve`）：

- `knowledge_base` 必须归属四类知识库之一：`process` / `quality` / `equipment` / `trace`，检索时可按子图限定范围；
- `knowledge_strict_metadata=True`（`Settings` 默认开启）时，按子图要求校验必需元数据维度（`process` / `version` / `alarm_code` / `device_type` / `product_code`）；
- 元数据缺失或文档过期的命中会写入 `KnowledgeHit.missing_filters` / `expired`，此时 `KnowledgeHit.valid_for_auto_action` 为 False——**此类知识只允许作为参考，不允许支撑自动动作**，方案应降级为人工确认；
- 检索打分规则：报警代码 +6、设备类型 +4、工序 +2、产品码 +2、关键词命中加权、过期 -2、高风险文档权威级 +0.5；
- Agent 生成方案时必须引用：使用了哪份 SOP、哪个版本、是否适用于当前设备类型 / 报警 / 工序、是否存在冲突规则。

## 8. 解决方案生成设计

智能体不能只输出自然语言，应输出结构化方案对象，便于后续做风险判断、函数调用、人工确认、审计追踪、执行结果回写、失败回滚或转人工。

### 8.1 方案对象

> 以下结构与 `src/industrial_agent/models/plan.py` **逐字段对齐**。早期文档中的独立 `Evidence` 类在代码中并不存在，`evidence` / `root_cause_hypotheses` / `knowledge_references` 均以 `list[dict]` 承载。方案生成由 `planning/builder.py` 的 `PlanBuilder` 完成，方案校验由同文件的 `PlanValidator` 完成，输出 `PlanValidationResult`（含 `issues` / `risk_escalated` / `confidence_adjusted`）。

```python
from typing import Literal

from pydantic import BaseModel, Field

RiskLevel = Literal["low", "medium", "high"]
ActionType = Literal[
    "query_only",
    "notify_user",
    "create_ticket_draft",
    "execute_safe_function",
    "request_human_confirm",
    "control_suggestion",
]


class ProposedAction(BaseModel):
    action_id: str
    action_type: ActionType
    title: str
    description: str = ""
    risk_level: RiskLevel = "low"
    requires_human_confirm: bool = False
    executable: bool = True
    tool_name: str | None = None
    tool_args: dict | None = None
    preconditions: list[str] = Field(default_factory=list)
    rollback_hint: str | None = None
    evidence_refs: list[str] = Field(default_factory=list)


class ResolutionPlan(BaseModel):
    plan_id: str
    incident_id: str
    problem_summary: str
    root_cause_hypotheses: list[dict] = Field(default_factory=list)
    evidence: list[dict] = Field(default_factory=list)
    knowledge_references: list[dict] = Field(default_factory=list)
    actions: list[ProposedAction] = Field(default_factory=list)
    user_instruction: str | None = None
    prohibitions: list[str] = Field(default_factory=list)
    data_gaps: list[str] = Field(default_factory=list)
    need_human_confirm: bool = False
    confidence: float = Field(default=0.0, ge=0, le=1)
    validity_note: str | None = None
```

### 8.2 方案内容要求

每个解决方案应包含：问题摘要、可能原因、证据链、引用的知识库文档、建议动作、风险等级、是否需要人工确认、用户操作提示、失败后的处理方式、回滚提示。

### 8.4 执行分流（与 `execution/executor.py` 的 `ActionExecutor` 对齐）

由 LangGraph 节点根据 `ResolutionPlan` 做**确定性分发**，不暴露给 LLM 随意调用。`ActionExecutor.plan_dispatch` 把方案动作按风险分入三个桶：

```python
def plan_dispatch(self, plan: ResolutionPlan) -> dict[str, list[ProposedAction]]:
    buckets = {"auto": [], "todo": [], "confirm": []}
    for action in plan.actions:
        if action.requires_human_confirm or action.risk_level == "high":
            buckets["confirm"].append(action)   # 需人工确认
        elif action.risk_level == "low":
            buckets["auto"].append(action)       # 低风险自动执行
        else:
            buckets["todo"].append(action)       # 中风险：灰度放开后自动执行，否则转人工待办
    return buckets
```

- `auto`：由 `execute_safe_actions` 节点执行，写动作受 `ToolContext.allow_write`（灰度 `allow_write`）约束。
- `todo`：由 `execute_medium_risk_actions` 节点处理；当灰度策略 `allow_medium_auto=False` 时**只留待办不自动执行**（写入 `deferred_actions`），放开后才执行。
- `confirm`：由 `request_human_confirm` 节点经 LangGraph `interrupt` 中断等待人工决策；同意后且灰度 `allow_high_confirm=True` 才真正执行，否则转 `deferred_manual` 人工待办。

`ActionExecutor.execute` 在真正调用工具前还会做前置再校验：幂等（`DUPLICATE_EXECUTION`）、高风险无确认（`CONFIRM_REQUIRED`）、确认状态无效（`CONFIRM_INVALID`）、不可执行（`NOT_EXECUTABLE`）、未绑定工具（`NO_TOOL_BOUND`），任意一项失败即拒绝执行并落审计。回滚由 `ActionExecutor.rollback` 提供（无 `rollback_hint` 时返回 `NO_ROLLBACK_PLAN` 并升级人工）。

## 9. 风险分级与执行边界

### 9.1 风险等级与四级灰度策略

三级风险等级与 `models/plan.py` 的 `RiskLevel`、`tools/contracts.py` 的 `ToolRisk` 对齐：

| 风险等级 | 示例 | 处理方式 |
|---|---|---|
| 低风险 | 查询状态、生成提示、记录诊断 | 可自动执行 |
| 中风险 | 创建工单草稿、通知责任人、生成处置建议 | 可生成草稿或通知，必须审计 |
| 高风险 | 停机、启机、改参数、冻结批次、改工单状态 | 必须人工确认 |

在此之上，`config.py` 定义了**四级灰度发布策略**（`RolloutPolicy`），由 `Settings.rollout_mode` 控制，决定写动作、中风险自动执行、高风险受控执行三组开关；未知模式一律按最保守的 `shadow` 处理（`rollout_policy`）。

| 灰度模式 | allow_write | allow_medium_auto | allow_high_confirm | 行为 |
|---|---|---|---|---|
| `shadow`（影子模式） | 否 | 否 | 否 | 只生成方案与诊断，不执行任何写操作；用于上线前观察 |
| `low_auto`（低风险自动） | 是 | 否 | 否 | 开放查询、诊断记录、工单草稿、通知；中风险动作留待办不自动执行 |
| `medium_auto`（中风险闭环） | 是 | 是 | 否 | 中风险待办确认流上线，自动执行中风险动作 |
| `high_controlled`（高风险受控） | 是 | 是 | 是 | 人工审批通过的高风险动作可受控执行 |

> A1 / B1 第一版只读智能体的写工具，即使 `allow_write=True` 也会被 `catalog.is_readonly` 拦截并返回 `WRITE_BLOCKED`。

### 9.2 执行原则

- 只读查询可以自动执行
- 分析判断可以自动执行，但必须输出证据
- 工单草稿、通知提示可以自动生成
- 控制建议只能生成，不能直接执行
- 高风险动作必须经过权限校验、参数校验、人工确认、审计和回滚策略
- 不允许 LLM 自行决定是否执行高风险动作

控制类工具必须包含：校验操作人权限、校验设备是否允许控制、校验参数范围、校验人工确认令牌、写入审计日志、调用底层控制接口、返回执行结果和回滚信息。第一版建议只做“控制请求 -> 生成操作建议 -> 等待人工确认 -> 不真正执行”。

## 10. 人工确认机制（与 `execution/executor.py` 的 `ConfirmStore` 对齐）

当方案含 `requires_human_confirm` 或 `risk_level == "high"` 的动作时（即 `ActionExecutor.plan_dispatch` 的 `confirm` 桶），`request_human_confirm` 节点会：

1. 调用 `ConfirmStore.create` 生成 `ConfirmRequest`（定义于 `models/execution.py`）；
2. 通过 LangGraph `interrupt` 中断当前事件处理，将确认请求推送给前端；
3. 人工决策后由 `api/app.py` 的确认回调端点 `POST /confirms/{thread_id}` 调用 `agent.resume`，经 LangGraph `Command(resume=...)` 恢复图执行；图在 `_request_human_confirm` 节点续跑时调用 `ConfirmStore.decide` 写入决策，再按灰度策略决定执行或转人工待办。

确认请求字段（`ConfirmRequest`）：`confirm_id`、`incident_id`、`plan_id`、`action_id`、`action_title`、`action_detail`、`tool_name`、`tool_args`、`risk_level`、`risks`、`rollback_hint`、`required_roles`、`assignee`、`created_at`、`expire_at`、`status`、`decision_by`、`decision_at`、`decision_note`。

确认状态机（`ConfirmStatus`）：`pending -> approved / rejected / expired`，执行后追加 `executed / failed`。

| 确认结果 | 系统动作（对齐 `ConfirmStore.decide` 与图节点） |
|---|---|
| 同意（approved） | 角色校验通过后置 `approved`；灰度 `allow_high_confirm=True` 时执行，否则转 `deferred_manual` 人工待办 |
| 拒绝（rejected） | 记录 `decision_note`，动作转人工处理，不落执行 |
| 超时（expired） | `expire_overdue` 将超时 pending 请求置 `expired`；**严禁默认同意**，需重新发起确认 |
| 角色不符 | `decide` 拒绝决策并返回缺失角色列表（`缺少确认角色`） |

关键安全约束（与代码一致）：
- 不存在、非 pending、已超时的确认请求均不可再次决策；
- `ActionExecutor.execute` 执行高风险动作前必须校验 `confirm_id` 对应请求状态为 `approved`，否则返回 `CONFIRM_REQUIRED` / `CONFIRM_INVALID`；
- 所有确认请求与决策均落审计（`confirm:request` / `confirm:decision`），`confirm_ttl_seconds` 控制默认超时（3600s）。

## 11. 状态设计

### 11.1 多智能体全局状态（与 `graph/state.py` 逐字段对齐）

> 早期文档中的扁平字段（`event_id` / `task_type` / `agent_results` / `human_confirm_status` / `error` 等）在实际代码中已重构为以下结构。`IndustrialAgentState` 是 `TypedDict(total=False)`，主图与子图共享同一状态对象。

```python
from typing import TypedDict


class IndustrialAgentState(TypedDict, total=False):
    event: dict                 # 标准化后的原始事件
    incident: dict              # 事件治理（去重/幂等/限流）后的事件对象
    incident_type: str          # INCIDENT_SUBGRAPH 分类结果
    subtasks: list[dict]        # 主调度拆解的子任务
    agent_codes: list[str]      # 实际路由到的智能体编码（受 FIRST_RELEASE_CODES 收敛）
    agent_findings: dict        # 各智能体原始发现（code -> findings）
    knowledge_refs: list[dict]  # 检索到的知识元数据
    merged_findings: dict       # merge_findings 节点合并后的统一发现
    resolution_plan: dict       # ResolutionPlan 的 dict 形式
    risk_level: str             # 方案最高风险等级 low / medium / high
    need_human_confirm: bool
    confirm_request: dict       # 人工确认中断时写入的 ConfirmRequest
    confirm_status: str         # pending / approved / rejected / expired
    executed_actions: list[dict]
    deferred_actions: list[dict]   # 因灰度/确认延迟，转人工待办的动作
    final_answer: str
    audit_log_id: str
    errors: list[dict]
    duplicate: bool             # 治理层判定重复
    throttled: bool             # 治理层判定限流
    validation_issues: list[dict]  # 方案校验问题
    node_trace: list[dict]      # 节点级轨迹，支撑回放
```

### 11.2 状态使用原则

主图和子图之间显式传递状态；子 Agent 只接收必要字段；子 Agent 返回结构化结果；所有关键判断必须保留证据；所有动作必须可审计；所有失败必须可追踪。该状态需支撑事件回放、多 Agent 结果合并、证据链追踪、风险判断、人工确认、写操作审计。

## 12. LangGraph 主流程设计（与 `graph/orchestrator.py` 对齐）

主图实际为 **14 个节点**，通过 `StateGraph(IndustrialAgentState)` 构建并 `compile(checkpointer=...)`（checkpointer 支撑人工确认中断后的 `resume`）。

```text
START
  -> normalize_event
      continue -> governance_check
      respond  -> respond
  -> governance_check
      continue -> classify_incident
      respond  -> respond
  -> classify_incident -> plan_subtasks -> retrieve_knowledge
      -> run_specialists -> merge_findings -> build_resolution_plan
      -> validate_plan
          safe    -> execute_safe_actions
          medium  -> execute_medium_risk_actions
          confirm -> request_human_confirm
          none    -> record_result
  -> execute_safe_actions -> execute_medium_risk_actions -> record_result
  -> request_human_confirm -> record_result
  -> record_result -> respond -> END
```

### 12.1 节点说明

| 节点 | 作用（对齐实现） |
|---|---|
| normalize_event | 多源事件标准化为 `event`，路由 `continue` / `respond` |
| governance_check | 去重（`duplicate`）、幂等、限流（`throttled`）、权限；命中拦截走 `respond` 直出 |
| classify_incident | 按 `INCIDENT_SUBGRAPH` 分类，写入 `incident_type` |
| plan_subtasks | 主调度拆解子任务，结合 `ROUTE_AGENT_MAP` + `FIRST_RELEASE_CODES` 收敛 `agent_codes` |
| retrieve_knowledge | 检索 SOP / 案例 / 维护记录，写入 `knowledge_refs`（在专家分析之前注入知识） |
| run_specialists | 执行 `agent_codes` 对应的专业智能体，写入 `agent_findings` |
| merge_findings | 合并各智能体发现为统一 `merged_findings` |
| build_resolution_plan | `PlanBuilder` 生成 `ResolutionPlan` |
| validate_plan | `PlanValidator` 校验，写入 `validation_issues`；按风险路由 |
| execute_safe_actions | 执行 `auto` 桶低风险动作（写动作受 `allow_write`） |
| execute_medium_risk_actions | 处理 `todo` 桶：`allow_medium_auto` 时执行，否则留 `deferred_actions` |
| request_human_confirm | `confirm` 桶经 `interrupt` 等待人工决策 |
| record_result | 落审计，写 `executed_actions` / `deferred_actions`，状态闭环 |
| respond | 生成 `final_answer` |

> 注意：知识检索（`retrieve_knowledge`）在专家分析（`run_specialists`）**之前**，确保智能体分析时已有知识上下文；早期文档将二者顺序写反，以本图为准。

### 12.2 风险路由（对齐 `_route_by_risk`）

```python
def _route_by_risk(self, state: IndustrialAgentState) -> str:
    plan_data = state.get("resolution_plan")
    if not plan_data:
        return "none"
    plan = ResolutionPlan.model_validate(plan_data)
    buckets = self._executor.plan_dispatch(plan)   # 复用三分桶结果，保证路由与执行分流一致
    if buckets["confirm"]:
        return "confirm"
    if any(a.executable for a in buckets["auto"]):
        return "safe"
    if any(a.executable for a in buckets["todo"]):
        return "medium"
    return "none"
```

`safe` 进入 `execute_safe_actions`（随后串联到 `execute_medium_risk_actions`，无中风险动作时为空转）；`medium` 直接进 `execute_medium_risk_actions`；`confirm` 经 `interrupt` 等待人工；`none` 跳过执行直落审计。`normalize_event` 与 `governance_check` 各自的条件路由在拦截命中时走 `respond` 直出最终答复，不进入后续分析。

### 12.3 主调度与路由规则

`classify_incident` + `plan_subtasks` 两个节点替代了早期的单一 `route_task` 节点：
- 分类基于 `catalog.INCIDENT_SUBGRAPH` 规则映射；`llm_enabled=True` 时，模糊表达可叠加 LLM 做结构化意图识别（降级模式，规则优先）；
- 路由到的智能体由 `catalog.ROUTE_AGENT_MAP` 决定，并受 `agent_release_scope="first"` 的 `FIRST_RELEASE_CODES` 收敛——第一版仅放行 A3 / B3 / B4 闭环，A1 / B1 仅作读取证；
- 控制类请求与高风险动作默认进入 `request_human_confirm`，不允许 LLM 自行决定是否执行；
- 行业特定处置规则通过 `catalog.INDUSTRY_INJECTION`（按 `tenant_id` / 行业）注入到方案生成上下文。

## 13. 典型业务闭环

> 本章为业务叙事视角。其中“生产异常 / 物料 / 质量追溯 / 设备诊断 / 维护建议”对应 `catalog.AGENT_CATALOG` 中的 **A3 / A2 / B4 / B3 / B4** 等子 Agent（第一版仅 A1 / A3 / B1 / B3 / B4 可用，A2 不在第一版范围，缺料类查询由 B3 的只读工具覆盖）；“知识检索”并非独立 Agent，而是主图的 `retrieve_knowledge` 节点，由主调度在 `dispatch_agents` 之前统一检索并分发给各子 Agent。各 Agent 的真实编号与边界见《智能体构建清单方案》“六”。

### 13.1 MES 工单阻塞，疑似缺料

```text
1. MES 推送工单阻塞事件
2. 事件治理层去重、判断优先级
3. 主调度识别为生产 + 物料复合问题
4. 生产异常 Agent 查询工单、工序、在制品、影响范围
5. 物料库存 Agent 查询库存、批次、库位、替代料
6. 质量追溯 Agent 检查批次是否冻结或检验异常
7. 知识检索节点 检索缺料处理 SOP
8. 主调度汇总原因、影响、可用资源和处理建议
9. 输出给计划员 / 班组长
10. 如需补料、改单、冻结，生成待确认动作
```

### 13.2 QMS 批次不良

```text
1. QMS 推送批次不良事件
2. 质量追溯 Agent 查询批次、工单、物料、设备、工艺参数
3. 生产异常 Agent 判断影响哪些在制工单
4. 物料库存 Agent 判断同批次库存是否仍在库或已发料
5. 设备诊断 Agent 检查相关设备是否存在异常
6. 知识检索节点 检索质量处置 SOP
7. 主调度生成隔离、复检、返工、停线建议
8. 高风险处置进入人工确认
```

### 13.3 设备异常

```text
1. 设备系统推送报警事件
2. 设备诊断 Agent 查询实时状态、报警、趋势、历史故障
3. 知识检索节点 检索 SOP 和历史案例
4. 维护建议 Agent 生成维护方案
5. 系统判断风险等级
6. 低风险：提示检查、生成工单草稿
7. 高风险：生成停机检查建议，等待人工确认
8. 记录处理结果并闭环
```

## 14. 给人工处理的提示格式

当系统判断需要人工处理时，应输出可执行提示，而不是笼统建议，让一线人员能直接按步骤处理。

```text
问题摘要：
设备 A-001 温度持续升高，触发高温报警。

判断依据：
1. 当前温度高于设定阈值。
2. 近 1 小时温度呈上升趋势。
3. 知识库 SOP 提示优先检查散热系统、冷却系统和负载情况。

建议人工操作：
1. 现场检查风扇、滤网、风道是否堵塞。
2. 检查冷却液液位、泵运行状态。
3. 核对当前负载是否超过工艺范围。
4. 如温度继续上升，按安全规程申请停机检查。

禁止事项：
1. 未确认安全前不要直接复位报警。
2. 未授权人员不要修改设备参数。
3. 不要跳过停机确认流程。

需要确认：
1. 是否创建维修工单。
2. 是否通知设备工程师。
3. 是否进入停机检查流程。
```

## 15. 审计与闭环记录

每次事件处理必须记录：事件 ID、trace_id、来源系统、事件类型、设备/工单/批次/物料信息、查询到的设备状态、查询到的业务数据、检索到的知识库文档、各 Agent 输出结果、最终解决方案、风险等级、是否调用函数、调用参数、执行结果、失败原因、是否转人工、人工确认结果、最终闭环状态。

> 实际落盘由三类 Pydantic 模型承载（`models/execution.py`）：工具前置检查链每步产生 `AuditRecord`（`actor` / `action` / `target` / `input_snapshot` / `output_snapshot` / `risk_level` / `decision` / `reason`，`decision` 取 `allowed` / `denied` / `confirmed` / `rejected` / `executed` / `rolled_back`）；每次动作执行产生 `ActionExecution`（`status` 取 `success` / `failed` / `partial` / `rolled_back`，含 `rollback_executed`）；需人工确认的动作产生 `ConfirmRequest`（`status` 取 `pending` / `approved` / `rejected` / `expired` / `executed` / `failed`）。

审计数据用于：问题回放、责任追踪、模型效果评估、知识库优化、工具失败分析、风险策略调整。

测试分三层：

1. 工具测试：模拟 Modbus/MQTT/OPC UA/数据库返回，验证解析和异常处理
2. 图流程测试：验证不同意图是否走正确分支
3. 端到端测试：用固定样例验证“设备异常 -> 查询数据 -> 汇总证据 -> 输出建议”

## 17. 与 WMS / MES / QMS 的集成方式

建议分三类接口：

| 类型 | 用途 | 风险 |
|---|---|---|
| 事件订阅 | WMS/MES/QMS 推送异常事件 | 低 |
| 只读查询 | Agent 查询工单、库存、批次、检验、设备状态 | 低 |
| 写操作 | 创建工单、冻结批次、修改状态、下发控制 | 高 |

第一阶段只做：事件订阅 + 只读查询 + 生成建议 + 生成工单草稿。

写操作必须经过治理层完整链路：

```text
Agent 提出动作建议 -> 权限校验 -> 业务规则校验 -> 风险等级判断
  -> 人工确认 -> 调用 WMS/MES/QMS 正式接口 -> 审计记录 + 回滚策略
```

## 18. 从 0 到 1 落地推进计划

### 阶段一：单智能体只读诊断（第 1-4 周）

| 周 | 目标 | 交付物 |
|---|---|---|
| 第 1 周 | 跑通 Python + uv + LangChain + LangGraph 最小项目 | 可运行 Agent Demo |
| 第 2 周 | 接入 1 个只读数据源 | 设备状态 / 报警查询工具 |
| 第 3 周 | 建立 LangGraph 状态图 | 意图识别、分支、工具调用、结果总结 |
| 第 4 周 | 接入知识库和追溯数据 | RAG 检索、证据链输出 |

### 阶段二：多智能体协同（第 5-8 周）

| 阶段 | 目标 | 能力边界 |
|---|---|---|
| 第 5 阶段 | 拆出 3 个专业 Agent | 设备状态、报警诊断、知识检索 |
| 第 6 阶段 | 引入主调度 | LangGraph 父图统一路由和汇总 |
| 第 7 阶段 | 加审计、日志、异常处理 | 可追踪、可复盘 |
| 第 8 阶段 | 设计人工确认机制 | 高风险动作不自动执行 |

### 阶段三：事件驱动业务闭环（第 9 周起）

| 阶段 | 目标 | 能力边界 |
|---|---|---|
| 第 9 阶段 | 接入 1 类事件（如 MES 工单异常） | 只读分析，生成建议 |
| 第 10 阶段 | 接入 WMS 缺料 / 库存异常 | 查询库存、批次、工单 |
| 第 11 阶段 | 接入 QMS 质量异常 | 批次追溯、影响范围分析 |
| 第 12 阶段 | 建立主调度 + 多子 Agent | 复合问题协同分析 |
| 第 13 阶段 | 增加工单草稿 / 处置建议 | 可写草稿，不直接改正式业务 |
| 第 14 阶段 | 引入人工确认后的受控写操作 | 权限、审计、回滚必须完整 |

## 19. 必须守住的安全边界

- 不让 Agent 直接访问数据库表
- 不让 Agent 直接绕过 WMS/MES/QMS 业务规则
- 不让子 Agent 直接互相调用控制接口
- 不让 LLM 自行判断是否可以执行高风险动作
- 不让重复事件重复触发分析或写操作
- 不让控制类动作跳过人工确认
- 不让审计日志缺失

核心原则：不是让 Agent “自己决定解决问题”，而是让 Agent 生成方案，治理层决定执行边界。低风险动作可以自动处理，高风险动作必须转人工确认。

## 20. 第一版建议范围

建议把第一版限定为：只读型工业诊断智能体（事件驱动）。

具备：查询设备状态、查询报警记录、查询追溯数据、检索 SOP 和维修案例、生成异常分析和建议、输出证据链、生成工单草稿、对控制类请求只做提示和人工确认。

暂不具备：自动下发控制指令、自动修改工艺参数、自动启停设备、无权限访问生产系统、无审计的执行链路。

> 与代码实现的精确对齐：第一版可用范围由 `agents/catalog.py` 的 `FIRST_RELEASE_CODES` 定义（取自 `AGENT_CATALOG` 中 `first_release=True` 的智能体），实际为 **A1 / A3 / B1 / B3 / B4** 五类：
> - `A3`（生产异常）、`B3`（调度决策主脑）、`B4`（维护建议）可形成“分析—方案—低/中风险执行”闭环；
> - `A1`（工单查询）、`B1`（设备状态）标记 `first_release_readonly=True`，仅作读取证，其写动作会被 `catalog.is_readonly` 拦截并返回 `WRITE_BLOCKED`，即使灰度放开写权限也不执行；
> - 其余 A2 / A4 / A5 / B2 / B5 / C1 / C2 / C3 归入 `FIRST_RELEASE_EXCLUDED`，第一版不路由。
>
> 运行时由 `Settings.agent_release_scope="first"`（默认）经 `catalog.resolve_codes` 收敛；设为 `"all"` 可放开全量路由。灰度发布默认 `rollout_mode="shadow"`，即不执行任何写操作。

## 21. 结论

本方案形成了一条清晰的演进主线：

```text
单智能体只读诊断
  -> LangGraph 状态图编排
    -> 主调度 + 多专业子 Agent 协同
      -> WMS/MES/QMS 事件驱动闭环
        -> 设备信息 + 知识库生成结构化解决方案
          -> 风险分级 + 受控函数调用 + 人工确认
```

技术底座始终是 LangChain（能力）+ LangGraph（编排）+ 自研工业工具层（执行边界）+ 统一治理层（安全）。

最适合的第一版不是“自动处理所有问题”，而是：

> 系统自动推送异常事件，AI 自动分析、追溯、汇总证据、生成处置建议，低风险动作自动处理，高风险动作等待人工确认。

这样既能体现多智能体协同价值，又能保证工业系统需要的稳定性、可追溯性和安全边界。
