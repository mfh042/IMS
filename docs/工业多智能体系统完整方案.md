# 工业多智能体系统完整方案
## WMS / MES / QMS 事件驱动 + LangChain / LangGraph 协同 + 知识库决策 + 受控执行

> 技术栈：Python + uv 包管理 | LangChain 能力底座 + LangGraph 多智能体编排 + 自研工业工具层
> 文档版本：v1.0 | 整理日期：2026-11-26

---

## 1. 方案目标

构建一个面向工业现场的多智能体协同系统，接入 WMS、MES、QMS、设备系统、知识库等业务与数据源，实现以下能力：

1. 自动接收生产、物料、质量、设备等异常事件
2. 自动调用多个专业智能体进行协同分析
3. 结合设备信息、业务数据和知识库生成解决方案
4. 根据风险等级决定自动处理、生成提示、创建工单草稿或转人工确认
5. 全过程可追溯、可审计、可回放、可回滚
6. 不绕过现有 WMS / MES / QMS 业务规则，不直接让大模型控制设备

系统的核心定位是：

> AI 智能体负责事件理解、信息检索、协同分析、方案生成、风险提示和低风险受控处理；高风险动作仍由业务系统、权限体系和人工确认共同约束。

### 架构选型总纲

```text
LangChain（智能体能力底座）+ LangGraph（多智能体流程编排）+ 自研工业工具层（确定性执行边界）
```

- LLM 负责理解和规划，工具层负责确定性执行，LangGraph 负责流程、分支、重试、审计和人工确认。
- 不要让 LLM 直接操作工业系统：所有工业动作必须封装成工具，由工具层做权限、参数校验、超时、审计和失败处理。

## 3. 技术选型建议

| 层级 | 推荐技术 | 作用 |
|---|---|---|
| 智能体能力层 | LangChain | 模型调用、工具封装、RAG、结构化输出 |
| 多智能体编排层 | LangGraph | 主调度、子图、条件路由、人工确认节点 |
| 事件接入层 | Kafka / RabbitMQ / Redis Stream / Pulsar | 接收 WMS、MES、QMS 等系统事件 |
| 工具适配层 | 自研 Adapter | 对接设备、数据库、WMS、MES、QMS、知识库 |
| 数据存储层 | PostgreSQL / 时序库 / 对象存储 | 业务数据、审计数据、文档、模型输入输出记录 |
| 知识库层 | 向量库 + 元数据库 | SOP、故障案例、维护记录、工艺规范检索 |
| 治理层 | 自研权限、审计、风险策略模块 | 控制高风险动作，保证安全边界 |

消息中间件选型不强制绑定某一种，应根据现有基础设施、吞吐要求、延迟要求、运维能力选择。高频设备告警场景更关注低延迟和流式处理；业务系统集成更关注可靠投递、幂等、死信和回放。

## 4. 事件驱动设计

### 4.1 事件来源

| 系统 | 典型事件 | 触发场景 |
|---|---|---|
| WMS | 缺料、库存不足、批次冻结、发料失败、库位异常 | 物料无法支撑生产或库存状态异常 |
| MES | 工单阻塞、工序异常、报工异常、停线、在制品异常 | 生产执行过程出现偏差 |
| QMS | 来料不合格、过程不良、终检异常、CAPA 触发 | 质量异常需要追溯和处置 |
| EAM / 设备系统 | 设备故障、参数越限、通讯中断、维保到期 | 设备状态异常影响生产 |

### 4.2 标准事件格式

所有系统推送给智能体平台的事件应统一格式，字段必须稳定，否则后续 Agent 路由、审计、回放都会混乱。

```json
{
  "event_id": "evt-20261126-000123",
  "event_type": "mes.work_order.blocked",
  "source_system": "MES",
  "occurred_at": "2026-11-26T10:20:00+08:00",
  "severity": "high",
  "tenant_id": "factory_a",
  "trace_id": "trace-8f3a92",
  "idempotency_key": "MES-WO20261126001-OP-20-blocked",
  "payload": {
    "work_order_id": "WO20261126001",
    "line_id": "LINE-03",
    "process_id": "OP-20",
    "material_id": "M-10023",
    "batch_id": "B20261126-08",
    "device_id": "DEVICE-A-001",
    "message": "工序阻塞，疑似缺料"
  }
}
```

### 4.3 事件治理层能力

事件进入 Agent 前，必须经过治理层处理，避免重复分析、告警风暴、成本失控、重复写操作和高风险误触发。

| 能力 | 说明 |
|---|---|
| 去重 | 同一设备、工单、批次重复异常只处理一次 |
| 聚合 | 多个相关报警合并为一个问题 |
| 限流 | 防止告警风暴打爆模型和工具 |
| 优先级 | 停线、批量质量异常、安全风险优先处理 |
| 幂等 | 同一事件重复消费不重复执行 |
| 死信队列 | 处理失败后进入人工兜底 |
| 审计 | 记录事件来源、处理过程、结果 |

## 5. 多智能体架构

### 5.1 主调度 Agent

主调度 Agent 不直接查设备、不直接控制设备，只负责任务编排：

- 识别事件类型
- 判断是单一问题还是复合问题
- 拆解子任务
- 选择专业 Agent
- 合并多个 Agent 的结果
- 判断证据是否充分
- 判断是否需要人工确认
- 生成最终输出

### 5.2 专业子 Agent

按工业职责拆分（而不是按模型能力拆分）：

| Agent | 职责 | 风险边界 |
|---|---|---|
| 生产异常 Agent | 分析工单阻塞、工序异常、停线影响 | 只读分析，生成建议 |
| 物料库存 Agent | 查询库存、批次、缺料、替代料 | 只读查询 |
| 质量追溯 Agent | 查询检验、批次、不良、追溯链 | 只读查询 |
| 设备诊断 Agent | 查询设备状态、报警、趋势、历史故障 | 只读查询 |
| 维护建议 Agent | 结合 SOP 和历史案例生成维护建议 | 可生成工单草稿 |
| 知识检索 Agent | 检索 SOP、工艺规范、故障案例 | 只读检索 |
| 控制建议 Agent | 生成控制建议，不直接执行控制 | 必须人工确认 |

每个 Agent 可以是一个 LangGraph 子图，内部有自己的流程，但对外只暴露清晰的输入和输出。父图和子图之间显式转换状态，子图只拿自己需要的信息并返回结构化结果，便于测试和排错。

### 5.3 推荐编排模式

第一阶段推荐 Supervisor 模式（控制流清晰，适合生产系统）：

```text
主调度 Agent
  |-- 生产异常 Agent
  |-- 物料库存 Agent
  |-- 质量追溯 Agent
  |-- 设备诊断 Agent
  |-- 维护建议 Agent
  -- 控制建议 Agent
```

第二阶段：层级模式（系统规模变大后，按运维 / 质量 / 生产运营 / 物料供应拆分子调度器）：

```text
总主调度
  |-- 设备运维子调度
  |-- 质量追溯子调度
  |-- 生产运营子调度
  -- 物料供应子调度
```

不建议第一阶段采用完全自由协作的 Swarm 模式：工业系统更重视确定性、可追溯性、权限边界和审计能力，主调度模式更稳。

## 6. 统一工具层设计

所有 Agent 必须通过统一工具层访问设备和业务系统，不允许每个 Agent 自己直连数据库、设备或控制接口（否则权限、审计、参数校验都会不一致）。

```text
所有 Agent -> 统一工具层 -> 统一适配器 -> 工业系统 / 设备 / 数据库 / 知识库
```

### 6.1 工具分类

| 类型 | 示例 | 是否可自动执行 |
|---|---|---|
| 只读工具 | 查询设备状态、报警、库存、工单、批次、检验记录 | 可以 |
| 低风险写工具 | 创建工单草稿、发送提示、记录诊断结果 | 可以，但必须审计 |
| 中风险写工具 | 生成待确认处置单、通知责任人 | 可生成草稿或通知 |
| 高风险工具 | 停机、启机、修改参数、冻结批次、修改工单状态 | 必须人工确认 |

### 6.2 工具层统一处理

工具层必须统一实现：参数校验、权限校验、超时控制、重试策略、幂等控制、数据脱敏、审计日志、失败降级、高风险动作拦截、控制动作人工确认。

工具设计要求：参数明确（用类型注解/Pydantic 约束）、返回结构化数据、超时/失败/无数据都有明确结果、工具内部不隐式执行高风险动作、每次调用记录审计日志。

### 6.3 工具封装示例

```python
from typing import Any

from langchain_core.tools import tool


@tool
def query_device_status(device_id: str) -> dict[str, Any]:
    """查询设备实时状态：状态、关键测点、采集时间、数据质量。"""
    # 真实项目中这里调用 Modbus / MQTT / OPC UA / 数据库适配器
    return {
        "device_id": device_id,
        "online": True,
        "temperature": 68.5,
        "vibration": 2.1,
        "data_quality": "good",
        "collected_at": "2026-11-26T10:00:00+08:00",
    }


@tool
def query_recent_alarms(device_id: str, hours: int = 24) -> list[dict[str, Any]]:
    """查询设备最近报警记录。"""
    return [
        {
            "alarm_code": "TEMP_HIGH",
            "level": "warning",
            "message": "温度超过阈值",
            "created_at": "2026-11-26T09:30:00+08:00",
        }
    ]
```

## 7. 知识库与设备信息融合

### 7.1 设备信息作用（回答“当前发生了什么”）

设备实时状态、测点数据、报警记录、历史趋势、运行参数、维保记录、故障历史、通讯状态。

### 7.2 知识库作用（回答“标准上应该怎么处理”）

SOP、工艺规范、故障处理手册、历史案例、安全注意事项、质量处置规则、维护流程、设备说明书。

### 7.3 检索推荐逻辑

```text
设备编号 + 报警代码 + 设备类型 + 异常关键词
  -> 检索 SOP
  -> 检索历史故障案例
  -> 检索维护记录
  -> 检索安全注意事项
  -> 生成候选方案
```

检索维度建议覆盖：设备编号、设备类型、报警代码、异常关键词、工单类型、物料类型、质量不良代码、时间范围。

检索建议区分数据类型：

- SOP、工艺规范、维修案例：适合 RAG
- 设备实时状态：必须走工具查询，不要让 LLM 猜
- 追溯数据：必须走数据库或业务系统接口
- 控制参数：必须有规则校验，不能只依赖模型输出

### 7.4 知识文档必须带元数据（防止错误方案被自动执行）

```json
{
  "doc_id": "SOP-DEVICE-001",
  "title": "设备高温报警处理流程",
  "version": "v3.2",
  "effective_date": "2026-01-01",
  "applicable_devices": ["DEVICE_TYPE_A"],
  "risk_level": "medium",
  "content": "......"
}
```

Agent 生成方案时要引用：使用了哪份 SOP、哪个版本、是否适用于当前设备类型、是否与当前报警匹配、是否存在冲突规则。如果知识文档过期、适用范围不匹配、证据不足，应降级为“建议人工确认”，不能自动执行。

## 8. 解决方案生成设计

智能体不能只输出自然语言，应输出结构化方案对象，便于后续做风险判断、函数调用、人工确认、审计追踪、执行结果回写、失败回滚或转人工。

### 8.1 方案对象

```python
from typing import Literal

from pydantic import BaseModel, Field


class Evidence(BaseModel):
    source: str = Field(description="数据来源，例如设备状态、报警、知识库")
    content: str = Field(description="关键证据内容")
    confidence: float = Field(ge=0, le=1, description="证据可信度")


class ProposedAction(BaseModel):
    action_type: Literal[
        "query_only",
        "notify_user",
        "create_ticket_draft",
        "execute_safe_function",
        "request_human_confirm",
        "control_suggestion",
    ]
    title: str
    description: str
    risk_level: Literal["low", "medium", "high"]
    requires_human_confirm: bool
    executable: bool
    tool_name: str | None = None
    tool_args: dict | None = None
    rollback_hint: str | None = None


class ResolutionPlan(BaseModel):
    problem_summary: str
    root_cause_hypotheses: list[str]
    evidence: list[Evidence]
    knowledge_references: list[str]
    actions: list[ProposedAction]
    user_instruction: str | None = None
    need_human_confirm: bool
    confidence: float = Field(ge=0, le=1)
```

### 8.2 方案内容要求

每个解决方案应包含：问题摘要、可能原因、证据链、引用的知识库文档、建议动作、风险等级、是否需要人工确认、用户操作提示、失败后的处理方式、回滚提示。

### 8.3 方案生成节点示例

```python
from langchain_core.tools import tool


@tool
def build_resolution_plan(
    device_id: str,
    device_status: dict,
    alarms: list[dict],
    knowledge_results: list[dict],
) -> dict:
    """根据设备状态、报警信息和知识库结果生成解决方案。"""
    # 这里可调用 LLM 做结构化输出，但输出必须符合 ResolutionPlan 结构
    return {
        "problem_summary": "设备温度持续升高，触发高温报警",
        "root_cause_hypotheses": ["散热异常", "负载过高", "温度传感器异常", "冷却系统故障"],
        "evidence": [
            {"source": "device_status", "content": "当前温度高于阈值", "confidence": 0.9},
            {"source": "knowledge_base", "content": "SOP 建议先检查散热和冷却系统", "confidence": 0.85},
        ],
        "actions": [
            {
                "action_type": "notify_user",
                "title": "提示人工检查散热系统",
                "description": "建议检查风扇、滤网、冷却液、风道是否堵塞。",
                "risk_level": "low",
                "requires_human_confirm": False,
                "executable": False,
            },
            {
                "action_type": "create_ticket_draft",
                "title": "生成维修工单草稿",
                "description": "将设备编号、报警信息、建议检查项写入工单草稿。",
                "risk_level": "medium",
                "requires_human_confirm": False,
                "executable": True,
                "tool_name": "create_maintenance_ticket_draft",
                "tool_args": {"device_id": device_id, "alarm": "TEMP_HIGH"},
            },
            {
                "action_type": "control_suggestion",
                "title": "建议停机检查",
                "description": "如温度继续上升，建议由授权人员确认后执行停机。",
                "risk_level": "high",
                "requires_human_confirm": True,
                "executable": False,
            },
        ],
        "need_human_confirm": True,
        "confidence": 0.82,
    }
```

注意：这个工具只是生成方案，不代表方案一定可以执行。是否执行要经过风险判断和治理层。

### 8.4 函数调用分发（不要暴露给 LLM 随意调用）

更推荐由 LangGraph 节点根据 `ResolutionPlan` 做确定性分发：

```python
def execute_action(action: ProposedAction, context: dict) -> dict:
    if action.risk_level == "high":
        return {
            "status": "waiting_human_confirm",
            "message": "高风险动作已提交人工确认，未执行。",
            "action": action.model_dump(),
        }

    if not action.executable or not action.tool_name:
        return {
            "status": "suggestion_only",
            "message": action.description,
            "action": action.model_dump(),
        }

    # 这里根据 tool_name 查找受控工具
    # 执行前必须做权限、参数、幂等、审计检查
    raise NotImplementedError("接入实际受控工具")
```

## 9. 风险分级与执行边界

### 9.1 风险等级

| 风险等级 | 示例 | 处理方式 |
|---|---|---|
| 低风险 | 查询状态、生成提示、记录诊断 | 可自动执行 |
| 中风险 | 创建工单草稿、通知责任人、生成处置建议 | 可生成草稿或通知，必须审计 |
| 高风险 | 停机、启机、改参数、冻结批次、改工单状态 | 必须人工确认 |

### 9.2 执行原则

- 只读查询可以自动执行
- 分析判断可以自动执行，但必须输出证据
- 工单草稿、通知提示可以自动生成
- 控制建议只能生成，不能直接执行
- 高风险动作必须经过权限校验、参数校验、人工确认、审计和回滚策略
- 不允许 LLM 自行决定是否执行高风险动作

控制类工具必须包含：校验操作人权限、校验设备是否允许控制、校验参数范围、校验人工确认令牌、写入审计日志、调用底层控制接口、返回执行结果和回滚信息。第一版建议只做“控制请求 -> 生成操作建议 -> 等待人工确认 -> 不真正执行”。

---

## 10. 人工确认机制

当方案涉及高风险动作时，系统应生成人工确认请求。

确认内容：事件 ID、设备/工单/批次/物料信息、问题摘要、判断依据、建议动作、风险说明、回滚方式、责任人、确认时限。

| 人工确认结果 | 系统动作 |
|---|---|
| 同意执行 | 调用受控业务接口执行 |
| 拒绝执行 | 记录原因，转人工处理 |
| 修改后执行 | 重新校验参数和风险 |
| 超时未确认 | 按预设策略升级通知或关闭 |

### 11.2 状态使用原则

主图和子图之间显式传递状态；子 Agent 只接收必要字段；子 Agent 返回结构化结果；所有关键判断必须保留证据；所有动作必须可审计；所有失败必须可追踪。该状态需支撑事件回放、多 Agent 结果合并、证据链追踪、风险判断、人工确认、写操作审计。

## 12. LangGraph 主流程设计

```text
START
  -> normalize_event
  -> governance_check
  -> route_task
  -> run_specialist_agents
  -> retrieve_knowledge
  -> build_resolution_plan
  -> validate_plan
  -> risk_route
      -> low：执行安全函数 / 发送提示
      -> medium：生成工单草稿 / 通知责任人
      -> high：提交人工确认
  -> record_result
  -> respond
  -> END
```

### 12.1 节点说明

| 节点 | 作用 |
|---|---|
| normalize_event | 将不同系统事件统一为标准结构 |
| governance_check | 去重、幂等、限流、权限检查 |
| route_task | 主调度判断任务类型和子 Agent |
| run_specialist_agents | 执行专业 Agent 分析 |
| retrieve_knowledge | 检索 SOP、案例、维护记录 |
| build_resolution_plan | 生成结构化解决方案 |
| validate_plan | 校验方案完整性、证据、适用范围 |
| risk_route | 根据风险等级路由 |
| record_result | 写入审计、结果、闭环状态 |

### 12.2 风险路由伪代码

```python
def risk_route(state: dict) -> str:
    plan = state.get("resolution_plan", {})

    if plan.get("need_human_confirm"):
        return "request_human_confirm"

    actions = plan.get("actions", [])
    risk_levels = [action.get("risk_level") for action in actions]

    if "high" in risk_levels:
        return "request_human_confirm"

    if "medium" in risk_levels:
        return "execute_medium_risk_actions"

    return "execute_safe_actions"
```

### 12.3 主调度图构建骨架

```python
from langgraph.graph import END, START, StateGraph


def build_supervisor_graph():
    graph = StateGraph(IndustrialAgentState)

    graph.add_node("normalize_event", normalize_event)
    graph.add_node("governance_check", governance_check)
    graph.add_node("route_task", route_task)
    graph.add_node("run_specialist_agents", run_specialist_agents)
    graph.add_node("retrieve_knowledge", retrieve_knowledge)
    graph.add_node("build_resolution_plan", build_resolution_plan)
    graph.add_node("validate_plan", validate_plan)
    graph.add_node("execute_safe_actions", execute_safe_actions)
    graph.add_node("execute_medium_risk_actions", execute_medium_risk_actions)
    graph.add_node("request_human_confirm", request_human_confirm)
    graph.add_node("record_result", record_result)
    graph.add_node("respond", respond)

    graph.add_edge(START, "normalize_event")
    graph.add_edge("normalize_event", "governance_check")
    graph.add_edge("governance_check", "route_task")
    graph.add_edge("route_task", "run_specialist_agents")
    graph.add_edge("run_specialist_agents", "retrieve_knowledge")
    graph.add_edge("retrieve_knowledge", "build_resolution_plan")
    graph.add_edge("build_resolution_plan", "validate_plan")

    graph.add_conditional_edges(
        "validate_plan",
        risk_route,
        {
            "execute_safe_actions": "execute_safe_actions",
            "execute_medium_risk_actions": "execute_medium_risk_actions",
            "request_human_confirm": "request_human_confirm",
        },
    )

    graph.add_edge("execute_safe_actions", "record_result")
    graph.add_edge("execute_medium_risk_actions", "record_result")
    graph.add_edge("request_human_confirm", "record_result")
    graph.add_edge("record_result", "respond")
    graph.add_edge("respond", END)

    return graph.compile()
```

`route_task` 可结合规则 + LLM：明确包含“查询状态”“报警”“追溯”“建议”等关键词时优先走规则，模糊表达再交给 LLM 做结构化意图识别，控制类请求默认进入人工确认。

## 13. 典型业务闭环

### 13.1 MES 工单阻塞，疑似缺料

```text
1. MES 推送工单阻塞事件
2. 事件治理层去重、判断优先级
3. 主调度识别为生产 + 物料复合问题
4. 生产异常 Agent 查询工单、工序、在制品、影响范围
5. 物料库存 Agent 查询库存、批次、库位、替代料
6. 质量追溯 Agent 检查批次是否冻结或检验异常
7. 知识检索 Agent 检索缺料处理 SOP
8. 主调度汇总原因、影响、可用资源和处理建议
9. 输出给计划员 / 班组长
10. 如需补料、改单、冻结，生成待确认动作
```

### 13.2 QMS 批次不良

```text
1. QMS 推送批次不良事件
2. 质量追溯 Agent 查询批次、工单、物料、设备、工艺参数
3. 生产异常 Agent 判断影响哪些在制工单
4. 物料库存 Agent 判断同批次库存是否仍在库或已发料
5. 设备诊断 Agent 检查相关设备是否存在异常
6. 知识检索 Agent 检索质量处置 SOP
7. 主调度生成隔离、复检、返工、停线建议
8. 高风险处置进入人工确认
```

### 13.3 设备异常

```text
1. 设备系统推送报警事件
2. 设备诊断 Agent 查询实时状态、报警、趋势、历史故障
3. 知识检索 Agent 检索 SOP 和历史案例
4. 维护建议 Agent 生成维护方案
5. 系统判断风险等级
6. 低风险：提示检查、生成工单草稿
7. 高风险：生成停机检查建议，等待人工确认
8. 记录处理结果并闭环
```

## 14. 给人工处理的提示格式

当系统判断需要人工处理时，应输出可执行提示，而不是笼统建议，让一线人员能直接按步骤处理。

```text
问题摘要：
设备 A-001 温度持续升高，触发高温报警。

判断依据：
1. 当前温度高于设定阈值。
2. 近 1 小时温度呈上升趋势。
3. 知识库 SOP 提示优先检查散热系统、冷却系统和负载情况。

建议人工操作：
1. 现场检查风扇、滤网、风道是否堵塞。
2. 检查冷却液液位、泵运行状态。
3. 核对当前负载是否超过工艺范围。
4. 如温度继续上升，按安全规程申请停机检查。

禁止事项：
1. 未确认安全前不要直接复位报警。
2. 未授权人员不要修改设备参数。
3. 不要跳过停机确认流程。

需要确认：
1. 是否创建维修工单。
2. 是否通知设备工程师。
3. 是否进入停机检查流程。
```

## 15. 审计与闭环记录

每次事件处理必须记录：事件 ID、trace_id、来源系统、事件类型、设备/工单/批次/物料信息、查询到的设备状态、查询到的业务数据、检索到的知识库文档、各 Agent 输出结果、最终解决方案、风险等级、是否调用函数、调用参数、执行结果、失败原因、是否转人工、人工确认结果、最终闭环状态。

测试分三层：

1. 工具测试：模拟 Modbus/MQTT/OPC UA/数据库返回，验证解析和异常处理
2. 图流程测试：验证不同意图是否走正确分支
3. 端到端测试：用固定样例验证“设备异常 -> 查询数据 -> 汇总证据 -> 输出建议”

## 17. 与 WMS / MES / QMS 的集成方式

建议分三类接口：

| 类型 | 用途 | 风险 |
|---|---|---|
| 事件订阅 | WMS/MES/QMS 推送异常事件 | 低 |
| 只读查询 | Agent 查询工单、库存、批次、检验、设备状态 | 低 |
| 写操作 | 创建工单、冻结批次、修改状态、下发控制 | 高 |

第一阶段只做：事件订阅 + 只读查询 + 生成建议 + 生成工单草稿。

写操作必须经过治理层完整链路：

```text
Agent 提出动作建议 -> 权限校验 -> 业务规则校验 -> 风险等级判断
  -> 人工确认 -> 调用 WMS/MES/QMS 正式接口 -> 审计记录 + 回滚策略
```

## 19. 必须守住的安全边界

- 不让 Agent 直接访问数据库表
- 不让 Agent 直接绕过 WMS/MES/QMS 业务规则
- 不让子 Agent 直接互相调用控制接口
- 不让 LLM 自行判断是否可以执行高风险动作
- 不让重复事件重复触发分析或写操作
- 不让控制类动作跳过人工确认
- 不让审计日志缺失

核心原则：不是让 Agent “自己决定解决问题”，而是让 Agent 生成方案，治理层决定执行边界。低风险动作可以自动处理，高风险动作必须转人工确认。

## 20. 第一版建议范围

建议把第一版限定为：只读型工业诊断智能体（事件驱动）。

具备：查询设备状态、查询报警记录、查询追溯数据、检索 SOP 和维修案例、生成异常分析和建议、输出证据链、生成工单草稿、对控制类请求只做提示和人工确认。

暂不具备：自动下发控制指令、自动修改工艺参数、自动启停设备、无权限访问生产系统、无审计的执行链路。

## 21. 结论

本方案形成了一条清晰的演进主线：

```text
单智能体只读诊断
  -> LangGraph 状态图编排
    -> 主调度 + 多专业子 Agent 协同
      -> WMS/MES/QMS 事件驱动闭环
        -> 设备信息 + 知识库生成结构化解决方案
          -> 风险分级 + 受控函数调用 + 人工确认
```

技术底座始终是 LangChain（能力）+ LangGraph（编排）+ 自研工业工具层（执行边界）+ 统一治理层（安全）。

最适合的第一版不是“自动处理所有问题”，而是：

> 系统自动推送异常事件，AI 自动分析、追溯、汇总证据、生成处置建议，低风险动作自动处理，高风险动作等待人工确认。

这样既能体现多智能体协同价值，又能保证工业系统需要的稳定性、可追溯性和安全边界。
