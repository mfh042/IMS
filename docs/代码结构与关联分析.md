# 工业多智能体系统 — 代码结构与关联分析

> 本文基于 `src/industrial_agent/` 当前代码库逐文件核对，描述每个文件的职责、对外接口，以及文件之间的 import / 调用 / 数据流转关联。与 `docs/工业多智能体系统完整方案.md` 互为补充：方案文档讲"为什么这样设计"，本文讲"代码里具体怎么组织、谁依赖谁"。

---

## 一、项目总览

- **主包**：`src/industrial_agent`（Python 3.12，`uv` 管理依赖，见 `pyproject.toml`）
- **编排底座**：LangChain + LangGraph（`StateGraph` + `InMemorySaver` 检查点 + `interrupt` 人工中断）
- **对外入口**：`api/app.py`（FastAPI HTTP 服务）与 `main.py`（命令行 CLI）
- **核心模式**：Supervisor 主调度（`IndustrialAgentGraph`）+ 13 类专业子 Agent 协同 + 统一工具入口 + 事件治理 + 知识约束 + 风险分级 + 灰度执行
- **配置体系**：`config.py` 的 `Settings`（环境变量 `IAMS_` 前缀，见 `.env.example`）

## 三、分层架构与依赖方向

代码严格遵循自底向上的单向依赖，无循环依赖。箭头表示"依赖 / import"：

```
┌───────────────────────────────────────────────────────────────┐
│  入口层   api/app.py ──┐                                        │
│           main.py ─────┤                                        │
└────────────────────────┼───────────────────────────────────────┘
                         ▼
┌───────────────────────────────────────────────────────────────┐
│  编排层           graph/orchestrator.py  （IndustrialAgentGraph）│
│   依赖几乎所有下层模块，是整个系统的中枢与唯一装配点              │
└──┬──────┬──────┬──────┬──────┬──────┬──────┬──────┬────────────┘
   ▼      ▼      ▼      ▼      ▼      ▼      ▼      ▼
┌───────────────────────────────────────────────────────────────┐
│  执行/装配层   execution/executor.py   agents/factory.py        │
│                tools/factory.py                                │
└──┬──────────────────┬───────────────────────┬─────────────────┘
   ▼                  ▼                       ▼
┌───────────────────────────────────────────────────────────────┐
│  服务层   tools/registry.py   planning/builder.py              │
│           agents/specialists.py  agents/base.py  agents/llm.py │
│           governance/governor.py  ingestion/normalizer.py      │
│           knowledge/store.py  audit/recorder.py                │
└──┬───────────────────────────────────────────────────────────┘
   ▼
┌───────────────────────────────────────────────────────────────┐
│  契约层   tools/contracts.py   agents/catalog.py               │
│           agents/industry.py                                   │
└──┬───────────────────────────────────────────────────────────┘
   ▼
┌───────────────────────────────────────────────────────────────┐
│  模型层   models/*.py （events/execution/findings/knowledge/plan）│
│           config.py                                            │
│  （零内部依赖，仅依赖 pydantic / 标准库，是全系统的最底层契约）   │
└───────────────────────────────────────────────────────────────┘
```

**关键约束**：
- `models/*` 与 `config.py` 不 import 任何同包模块，是最底层。
- `tools/contracts.py` 只依赖 pydantic，定义工具契约；`tools/registry.py` 依赖 `contracts` + `audit`。
- `orchestrator.py` 是唯一把所有子系统装配起来的地方（`__init__` 中构建 normalizer / governance / knowledge / tools / agents / builder / executor / audit）。
- 子系统之间不互相直接调用（如 `governor` 不调用 `normalizer`），一律由 `orchestrator` 按图节点顺序串联，保证流程确定性与可回放。

## 四、各文件功能详述（按模块）

### 4.1 根包：`__init__.py` / `config.py` / `main.py`

| 文件 | 功能 | 关键对外接口 |
|---|---|---|
| `__init__.py` | 包入口，仅 re-export 配置 | `Settings`, `get_settings` |
| `config.py` | 全局配置与灰度策略。`Settings` 继承 `BaseSettings`，环境变量前缀 `IAMS_`；`RolloutPolicy` 定义四级灰度开关矩阵（`allow_write` / `allow_medium_auto` / `allow_high_confirm`）；`rollout_policy(mode)` 按模式返回策略，未知模式回落 `shadow`；`agent_release_scope` 控制第一版范围收敛（默认 `first`）；`ensure_dirs()` 创建数据/知识/审计目录 | `Settings`, `get_settings()`（`lru_cache` 单例）, `rollout_policy()`, `RolloutPolicy`, `ROLLOUT_POLICY` |
| `main.py` | CLI 入口。解析 `--event`（事件 JSON，缺省内置示例）、`--thread-id`、`--approve/--reject`、`--decision-by`、`--role`、`--audit`；构造 `IndustrialAgentGraph`，跑 `run` 或 `resume`，打印 `final_answer` 与可选审计回放 | `main()` |

### 4.2 数据模型层 `models/`（最底层，零内部依赖）

全部基于 pydantic，是跨模块传递数据的唯一契约。

| 文件 | 定义内容 | 被谁使用 |
|---|---|---|
| `events.py` | `Severity`（low/medium/high/critical）、`DataQuality`（complete/partial/suspicious）、`StandardEvent`（标准化事件，顶层含 trace_id/idempotency_key/event_type/source_system/occurred_at/severity/tenant_id 及 device/wo/material/batch 等实体字段 + payload/raw_payload/data_quality）、`Incident`（治理后事件：incident_id/event_ids/incident_type/severity/priority_score/entity_refs/status）、`NormalizationOutcome`（ok/event 或 dead_letter_reason/error_code）、`IncidentType`（7 类：equipment/quality/material/production/query/standalone/mixed_exception） | `ingestion/normalizer.py`, `governance/governor.py`, `graph/orchestrator.py`, `planning/builder.py`, `agents/base.py` |
| `execution.py` | `ConfirmRequest`（人工确认请求：confirm_id/incident_id/plan_id/action_id/tool/args/risk/status/created_at/expires_at/decision 等）、`ActionExecution`（动作执行记录）、`AuditRecord`（审计记录：audit_id/trace_id/actor/action/target/input/output/risk/decision/created_at）、相关枚举（`ConfirmStatus`、`AuditDecision` 等） | `audit/recorder.py`, `execution/executor.py`, `graph/orchestrator.py` |
| `findings.py` | `AgentFinding`（子 Agent 输出：agent_name/summary/findings/hypotheses/evidence/knowledge_refs/confidence/data_gaps/suggested_next_steps/risk_notes） | 全部子 Agent、`planning/builder.py`、`agents/base.py`、`graph/orchestrator.py` |
| `knowledge.py` | `KnowledgeBase`（四类枚举：device_knowledge/maintenance_knowledge/esop_knowledge/quality_knowledge）、`KnowledgeChunk`（16 字段知识分块）、`KnowledgeHit`（命中结果：chunk + score + expired + reasons + `valid_for_auto_action`） | `knowledge/store.py`, `agents/base.py`, `planning/builder.py`, `graph/orchestrator.py` |
| `plan.py` | `RiskLevel`（low/medium/high）、`ProposedAction`（action_id/action_type/title/description/risk_level/requires_human_confirm/executable/tool_name/tool_args/preconditions/evidence_refs/rollback_hint）、`ResolutionPlan`（plan_id + 汇总）、`PlanValidationResult` / `PlanValidationIssue` | `planning/builder.py`, `execution/executor.py`, `graph/orchestrator.py` |

### 4.3 事件接入 `ingestion/normalizer.py`

- **职责**：把 WMS/MES/QMS/EAM/MANUAL 的异构原始报文转换为统一的 `StandardEvent`，对应方案"阶段 1"。
- **处理顺序**（`normalize()`）：非空校验 → 提取 `event_type`（顶层或 payload）→ 校验 `source_system` 白名单 → 时间解析与纠偏（无时区按 UTC、未来/历史偏移按接收时间）→ severity 规范化（非法降级 medium）→ 关键字段缺失检测 → 实体字段抽取 → `data_quality` 标记 → 生成 trace_id / idempotency_key → 构造 `StandardEvent`。
- **失败处理**：返回 `NormalizationOutcome(ok=False, dead_letter_reason, error_code)`，错误码含 `EMPTY_PAYLOAD` / `MISSING_EVENT_TYPE` / `INVALID_SOURCE_SYSTEM` / `INVALID_TIMESTAMP`。
- **关联**：只依赖 `models/events.py`；被 `graph/orchestrator.py` 的 `normalize_event` 节点调用。

### 4.4 事件治理 `governance/governor.py`

- **职责**：把 `StandardEvent` 流治理为 `Incident` 流，对应"阶段 2"，含去重、聚合、限流、优先级四步。
- **核心类 `EventGovernance`**：
  - `is_duplicate(event)`：按 `idempotency_key` 在去重窗口（默认 300s）内判重，重复计数累加。
  - `aggregate_key(event)` / `aggregate(event)`：按 `device:id:alarm` 或 `wo:id:process` 或 `batch:id:...` 聚合键合并为 `_Aggregate`，记录最大严重度、实体引用、影响产线、安全/高影响标记。
  - `_incident_type(event)`：按 event_type 前缀映射 incident 类型（mes→production、wms→material、qms→quality、eam→equipment、query/esop/manual→query、training/edu→standalone）。
  - `is_throttled(agg)`：全局并发上限（默认 8）+ 单实体上限（默认 2），超限返回原因。
  - `priority_score(agg, now)`：严重度权重 + 事件数 + 影响线数 + 高影响/安全加权 + 等待时长加权。
  - `build_incident(agg, now)`：生成 `Incident` 并登记到 `_open_incidents` / `_entity_open`。
  - `close_incident()` / `open_incidents()` / `rank_open_incidents()`：生命周期管理。
- **关联**：只依赖 `models/events.py`；被 `orchestrator` 的 `governance_check` 节点调用。

### 4.5 知识库 `knowledge/store.py`

- **职责**：知识分块加载、检索、元数据校验，对应"阶段 3"。
- **核心类 `KnowledgeStore`**：
  - 从 `settings.knowledge_path` 加载 JSON 分块，缺失时使用内置种子知识。
  - `classify_base(chunk)` 四类知识库归属逻辑（device/maintenance/esop/quality）。
  - `retrieve(...)`：按关键词/实体/知识库过滤检索，打分规则（标题命中 +6、正文 +4、告警码 +2、设备类型 +2、加权求和、过期 -2、版本最新 +0.5）。
  - 元数据校验：必需维度缺失时 `valid_for_auto_action=False`，禁止自动动作。
  - `KnowledgeHit.expired` 与 `valid_for_auto_action` 约束下游规划与执行。
- **关联**：依赖 `models/knowledge.py`；被 `orchestrator` 的 `retrieve_knowledge` 节点、`agents/base.py`（`AgentContext.knowledge`）、`planning/builder.py` 使用。

### 4.6 统一工具层 `tools/`

**`contracts.py`（契约）**
- `ToolKind = Literal["read","write","control"]`、`ToolRisk = Literal["low","medium","high"]`：工具的 kind（操作性质）与 risk（风险）双维度。
- `ToolContext`：工具调用上下文（trace_id/incident_id/actor/roles/tenant_id/**allow_high_risk**/**allow_write**）。`allow_write=False` 时统一拦截 write/control，用于只读取证 Agent（A1/B1）与影子模式。
- `ToolResult`：统一返回（ok/data/error_code/error_message/source/fetched_at/degraded）。
- `ToolSpec`（frozen dataclass）：工具规格（name/description/kind/risk/required_roles/retryable/timeout_seconds/handler）+ `auto_executable` 属性（risk != high）。

**`adapters.py`（数据源示例）**
- `IndustrialAdapter`：内存示例数据源，真实项目替换为 WMS/MES/QMS/EAM 接口。内置设备/报警/工单/库存/批次/质量记录的种子数据，以及 `create_ticket_draft` / `notify` / `control` / `load_esop` / `bind_codes` / `adjust_delivery_route` / `create_dispatch_suggestion` / `reuse_process_template` / `training_score` 等方法。
- 无内部依赖，仅标准库。

**`registry.py`（唯一入口 + 检查链）**
- `ToolRegistry`：所有智能体访问外部系统的**唯一入口**，维护 `_tools: dict[str, ToolSpec]`。
- `invoke(name, args, context)` 执行九步前置检查链：存在性 → 权限（required_roles）→ 高风险拦截（`allow_high_risk`）→ 写拦截（`allow_write` + kind）→ 幂等（`_idempotency` 缓存）→ 审计（执行前 record）→ 执行 handler → 审计（执行后 record）→ 结果缓存。
- `catalog()`：返回工具清单（供 API `/tools` 与 Agent 可见性控制）。
- 依赖：`tools/contracts.py` + `audit/recorder.py`。

**`factory.py`（工具装配）**
- `build_default_registry(adapter, audit)`：把 17 个 `ToolSpec` 注册进 `ToolRegistry`，包括 read 类（query_device_status/query_recent_alarms/query_device_trend/query_work_order/query_material_stock/query_batch/query_quality_record）、write 类（create_ticket_draft/send_notification/load_esop/bind_codes/adjust_delivery_route/create_dispatch_suggestion/training_score/reuse_process_template）、control 类（control_device/freeze_batch）。
- 依赖：`contracts.py` + `adapters.py` + `registry.py`。
- 被 `orchestrator.__init__` 调用一次，构建全图共享的工具注册中心。

### 4.7 审计 `audit/recorder.py`

- `AuditRecorder`：内存列表 + JSONL 落盘（`audit-{YYYYMMDD}.jsonl`），支持按 `trace_id` 回放。
- `record(...)`：构造 `AuditRecord`（`aud-` + uuid12），追加内存 + 落盘。
- `replay(trace_id)` / `dump_json(trace_id)` / `records()` / `clear()`。
- 依赖：`models/execution.py`（`AuditRecord`）。
- 被全系统共享：`ToolRegistry`、`BaseAgent`、`ActionExecutor`、`orchestrator` 各节点都会调用 `record`。

### 4.8 智能体层 `agents/`

**`base.py`（基类与共享上下文）**
- `AgentContext`（dataclass）：子 Agent 运行时上下文 — `incident` / `tool_context` / `tools`（ToolRegistry）/ `knowledge` / `llm`（可选）/ `scenario` / `tool_results` / `knowledge_hits`。
- `BaseAgent`：模板方法 `analyze(ctx)` 调用抽象 `_analyze(ctx)` 并自动写审计（`agent:analyze`）；提供 `_call(ctx, tool_name, **args)`（经 `ctx.tools.invoke` 调用工具并缓存结果）与 `_llm_finding(ctx)`（调 LLM 结构化输出，未启用返回 None 走规则降级）。
- 依赖：`llm.py`、`audit/recorder.py`、`knowledge/store.py`、`models/{events,findings,knowledge}.py`、`tools/{contracts,registry}.py`。

**`llm.py`（可选 LLM 增强）**
- `PROMPT_TEMPLATE`：提示词骨架（角色/输入/5 条约束：不编造、给证据、区分事实假设、不输出控制指令、严格 JSON）。
- `LLMClient`：基于 `langchain_openai.ChatOpenAI.with_structured_output(AgentFinding)`；`enabled` 取决于 `settings.llm_enabled` 与 `llm_api_key`；`structured_finding(...)` 失败重试 2 次后返回 None（规则降级）。
- 依赖：`config.py`、`models/findings.py`。

**`industry.py`（C1–C3 行业规则包）**
- `IndustryRulePack`（frozen dataclass）：code/title/checks/confirm_notes/template_hint。
- `INDUSTRY_RULE_PACKS`：C1 轨道装备多品种小批量、C2 航空高可靠、C3 新产品导入快速换型，各含行业校验项、确认边界、可选工艺模板。
- `rule_pack(code)`：非 C 类返回 None。
- 无内部依赖（仅 dataclass）。

**`catalog.py`（13 类智能体唯一事实来源）**
- `AGENT_CATALOG`：13 类智能体（A1–A5 / B1–B5 / C1–C3）的编号、名称、子图、确认边界、风险上限、工具/知识库对齐。
- `INCIDENT_SUBGRAPH`：incident 类型 → 子图映射。
- `ROUTE_AGENT_MAP`：7 条路由链（equipment→[A1,B3]、quality→[A3,B4] 等）。
- `INDUSTRY_INJECTION`：行业代码 → 注入的 C 类智能体（+C1/+C2/+C3）。
- `FIRST_RELEASE_CODES`：第一版启用范围（A1/A3/B1/B3/B4，其中 A1/B1 只读）。
- `resolve_codes(...)` / `is_readonly(code)` / `agent_name_of(code)` / `knowledge_bases_for(code)` / `required_knowledge_for(code)`：辅助查询。
- 无内部依赖（纯常量与函数），是 `orchestrator` 路由与范围控制的事实来源。

**`specialists.py`（子 Agent 具体实现）**
- **当前启用的 13 类**（由 `factory.py` 装配进主图）：
  - A1 `StationAssemblyAgent`（工位装配，第一版只读取证）
  - A2 `MaterialDeliveryAgent`（物料配送）
  - A3 `QualityTraceAgent`（质量追溯）
  - A4 `LineDispatchAgent`（产线调度）
  - A5 `TrainingTeachingAgent`（实训教学，独立链路）
  - B1 `AssemblyEntryAgent`（装配入口/E-SOP，第一版只读）
  - B2 `LogisticsServiceAgent`（物流服务）
  - B3 `ControlCenterAgent`（智能管控主分析脑，跨域取证；未知编号回落至此）
  - B4 `QualityTraceServiceAgent`（质量追溯服务）
  - B5 `TrainingServiceAgent`（实训服务）
  - C1/C2/C3 `IndustryRuleAgent`（行业规则注入，不调用工具、不自由协作，由 `factory` 传入 `IndustryRulePack`）
- **早期遗留类**（保留在文件中但**未接入主图**，`CODE_AGENT_CLASS` 未映射）：`EquipmentDiagnosisAgent`、`MaintenanceAdviceAgent`、`KnowledgeRetrievalAgent`、`ProductionExceptionAgent`、`MaterialInventoryAgent`、`ControlSuggestionAgent`。这些是阶段 5 早期的通用 Agent，已被 catalog 体系的 13 类取代，当前仅作历史参考。
- 每个子类实现 `_analyze(ctx)`：先取 `ctx.incident.entity_refs`，用 `_call` 调只读工具取证，再 `_llm_finding` 尝试 LLM 增强（成功则直接返回），否则走规则兜底计算 confidence、组装 `AgentFinding`。所有 `risk_notes` 明确声明不执行控制。
- 依赖：`base.py`、`models/findings.py`。

**`factory.py`（编号 → 实例装配）**
- `CODE_AGENT_CLASS`：A1–A5 / B1–B5 → 对应 specialists 类的映射。
- `is_industry_code(code)`：判断 C1–C3。
- `build_agent(code, audit)`：C 类 → `industry.rule_pack` + `IndustryRuleAgent`；未知编号 → 回落 `ControlCenterAgent`（B3）避免编排断链；其余查表实例化。
- 依赖：`industry.py`、`base.py`、`specialists.py`、`audit/recorder.py`。
- 被 `orchestrator` 按需调用（每个 thread 按路由 codes 构造子 Agent）。

### 4.9 方案生成 `planning/builder.py`

- `RiskClassifier.classify(...)`：规则优先风险分级 — `control_suggestion` 或 control 工具 → high；`notify_user`/`create_ticket_draft`/`execute_safe_function` → medium；其余 → low；数据质量 partial/suspicious、知识过期、有冲突时 `_escalate` 升级一级。
- `PlanBuilder.build(...)`：把多个 `AgentFinding` 汇总为 `ResolutionPlan` — 合并 evidence/data_gaps/hypotheses，构造 knowledge_refs，计算保守置信度（取 agent 下限/证据/知识三者最小值再减 gap 惩罚），按 incident_type 生成 `ProposedAction` 列表（设备异常 4 步：复核→建维护草稿→通知→确认停机；缺料/生产 3 步；质量 3 步；证据不足兜底）。
- `PlanValidator.validate(plan)`：校验清单 — 低置信度转人工、高风险缺确认标记、可执行缺前置条件、控制建议/控制工具不得可执行、缺证据引用、置信度与数据缺口不匹配下调；修正 `requires_human_confirm` / `executable` / `confidence`。
- `findings_evidence(findings)`：辅助函数，汇总所有 finding 的 evidence。
- 依赖：`models/{events,findings,knowledge,plan}.py`。

### 4.10 执行与人工确认 `execution/executor.py`

- `ConfirmStore`：人工确认请求存储。`create(...)` 生成 `ConfirmRequest`（`cfm-` + uuid10，含 TTL 默认 3600s）；`get` / `decide(confirm_id, approved, ...)`（批准→approved，拒绝→rejected，超时→expired，**严禁默认同意**）；`pending` / `expired` 状态维护。
- `ActionExecutor`：
  - `plan_dispatch(plan, policy)`：**三分桶** — `auto_actions`（低风险且 executable 且策略允许写）、`todo_actions`（中风险待办，medium_auto 模式才放可执行）、`confirm_actions`（高风险 requires_human_confirm）。
  - `execute(action, ctx, policy)`：执行前置再校验（策略/executable/工具存在）→ 调 `ToolRegistry` → 成功/失败审计 → 失败尝试回滚（`rollback_hint`）。
  - 依赖：`audit/recorder.py`、`models/{execution,plan}.py`、`tools/{contracts,registry}.py`。
- 被 `orchestrator` 的 `execute_safe_actions` / `execute_medium_risk_actions` / `_request_human_confirm` 节点调用。

### 4.11 编排中枢 `graph/`

**`state.py`（状态契约）**
- `IndustrialAgentState`（TypedDict，22 字段）：在 LangGraph 节点间流转的全部状态 — `event_raw` / `normalized_event` / `data_quality` / `governed` / `incident` / `incident_type` / `agent_codes` / `route_plan` / `knowledge_hits` / `knowledge_valid_for_auto` / `findings` / `resolution_plan` / `validation_result` / `auto_actions` / `todo_actions` / `confirm_actions` / `execution_results` / `confirm_requests` / `confirmations` / `audit_records` / `interrupt_state` / `final_answer`。

**`orchestrator.py`（14 节点主图，系统中枢）**
- `IndustrialAgentGraph`：构造时装配全部子系统（`Settings` → normalizer / governance / knowledge / tools(factory) / audit / LLM / builder / validator / executor / confirm_store），构建 `StateGraph` 并编译（`InMemorySaver` 检查点）。
- 14 节点与边：
  ```
  START → normalize_event → governance_check → classify_incident → plan_subtasks
        → retrieve_knowledge → run_specialists → merge_findings
        → build_resolution_plan → validate_plan → risk_route
        → execute_safe_actions / execute_medium_risk_actions / request_human_confirm
        → record_result → respond → END
  ```
  （`retrieve_knowledge` 在 `run_specialists` 之前，知识先于专家取证。）
- 关键节点逻辑：
  - `normalize_event`：调 `EventNormalizer.normalize`，失败写 final_answer 并跳过。
  - `governance_check`：去重 → 聚合 → 限流 → `build_incident`。
  - `classify_incident` / `plan_subtasks`：按 `catalog.resolve_codes` 路由子 Agent 链 + 行业注入，受 `agent_release_scope=first` 收敛。
  - `retrieve_knowledge`：按路由 Agent 的 `knowledge_bases_for` 检索，校验 `valid_for_auto_action`。
  - `run_specialists`：`ThreadPoolExecutor` 并行跑 `build_agent(code).analyze(AgentContext(...))`，只读取证 Agent 传 `allow_write=False`。
  - `build_resolution_plan` / `validate_plan`：`PlanBuilder` + `PlanValidator`。
  - `risk_route`：复用 `ActionExecutor.plan_dispatch` 三分桶（与执行分流同源），按 `executable` 标志路由到 auto / todo / confirm 分支。
  - `request_human_confirm`：`ConfirmStore.create` → `interrupt()` 挂起图，等人工 `Command(resume=...)` 恢复后调 `ConfirmStore.decide`。
  - `record_result` / `respond`：汇总审计，写 `final_answer`。
- 对外方法：`run(event_raw, thread_id)`、`resume(thread_id, decision)`、`replay(trace_id)`、`tools`、`governance` 属性。
- 依赖：几乎全部下层模块（见顶部 import 列表），是全系统唯一的装配点。

### 4.12 HTTP 服务 `api/app.py`

- `create_app(graph=None)`：构造 FastAPI，注入 `IndustrialAgentGraph`（缺省自建）。
- 路由：
  - `GET /health`：健康检查（env / tenant_id）。
  - `GET /tools`：工具目录（`agent.tools.catalog()`）。
  - `GET /incidents/open`：开放事件列表（`agent.governance.open_incidents()`）。
  - `POST /events`：事件接入（`EventIn`）→ `agent.run`。
  - `POST /confirms/{thread_id}`：人工确认回调（`ConfirmIn`）→ `agent.resume`。
  - `GET /audit/{trace_id}`：审计回放（`agent.replay`）。
- 依赖：`config.py`、`graph/orchestrator.py`。
- 是生产环境的主入口；`main.py` 是开发/调试用 CLI。

## 六、运行时数据流（端到端关联）

一次事件从接入到结案的完整调用链，串起所有模块：

```
原始报文（dict）
  │
  ▼  api/app.py  POST /events   或   main.py  --event
  │
  ▼  graph/orchestrator.py : run()
  │
  ├─[1] normalize_event ──► ingestion/normalizer.py : EventNormalizer.normalize()
  │                         └─► models/events.py  构造 StandardEvent
  │
  ├─[2] governance_check ──► governance/governor.py : is_duplicate → aggregate → is_throttled → build_incident
  │                          └─► models/events.py  构造 Incident
  │
  ├─[3] classify_incident ──► agents/catalog.py : resolve_codes()  查 ROUTE_AGENT_MAP + INDUSTRY_INJECTION
  │    plan_subtasks         （受 agent_release_scope=first 收敛到 A1/A3/B1/B3/B4）
  │
  ├─[4] retrieve_knowledge ──► knowledge/store.py : KnowledgeStore.retrieve()
  │                           └─► models/knowledge.py  构造 KnowledgeHit[]（含 valid_for_auto_action）
  │
  ├─[5] run_specialists ──► agents/factory.py : build_agent(code)  ←── agents/catalog.py
  │    （ThreadPool 并行）    └─► agents/specialists.py 子类 : BaseAgent.analyze()
  │                              ├─► agents/base.py : _call() ──► tools/registry.py : ToolRegistry.invoke()
  │                              │                        └─► tools/adapters.py : IndustrialAdapter（真实系统接口）
  │                              │                        └─► audit/recorder.py  写审计
  │                              └─► agents/base.py : _llm_finding() ──► agents/llm.py : LLMClient（可选）
  │                              └─► models/findings.py  输出 AgentFinding
  │
  ├─[6] merge_findings ──► 合并 dict[agent_name → AgentFinding]
  │
  ├─[7] build_resolution_plan ──► planning/builder.py : PlanBuilder.build()
  │                              └─► models/plan.py  构造 ResolutionPlan + ProposedAction[]
  │
  ├─[8] validate_plan ──► planning/builder.py : PlanValidator.validate()  修正风险/可执行标志
  │
  ├─[9] risk_route ──► execution/executor.py : ActionExecutor.plan_dispatch()  三分桶
  │                   └─► config.py : rollout_policy()  灰度开关
  │
  ├─[10] execute_safe_actions ──► ActionExecutor.execute() ──► ToolRegistry.invoke()（低风险自动）
  │     execute_medium_risk_actions（medium_auto 模式）
  │
  ├─[11] request_human_confirm ──► execution/executor.py : ConfirmStore.create()
  │      （高风险分支）          └─► langgraph interrupt()  挂起图
  │                               人工通过 POST /confirms/{thread_id} 或 CLI --approve 恢复
  │                               └─► orchestrator.resume() → Command(resume) → ConfirmStore.decide()
  │
  ├─[12] record_result ──► audit/recorder.py : AuditRecorder.record()（全链路审计）
```

**关键数据载体的流转**：
- `StandardEvent`（models/events）：normalizer 产出 → governance 消费。
- `Incident`（models/events）：governance 产出 → orchestrator/classify/retrieve/run_specialists 全程携带 → builder 消费。
- `AgentFinding`（models/findings）：specialists 产出 → merge → builder 消费。
- `KnowledgeHit`（models/knowledge）：store 产出 → 注入 AgentContext → builder 消费（过期判断）。
- `ResolutionPlan` / `ProposedAction`（models/plan）：builder 产出 → validator 修正 → executor 三分桶 + 执行。
- `ConfirmRequest` / `ActionExecution` / `AuditRecord`（models/execution）：executor / recorder 产出 → 审计回放。

## 七、第一版范围与模块启用关系

`config.Settings.agent_release_scope` 默认 `"first"`，在 `orchestrator` 路由时经 `catalog.resolve_codes` 收敛：

```
agent_release_scope = "first"
   │
   ▼  catalog.py : FIRST_RELEASE_CODES = {"A1","A3","B1","B3","B4"}
   │
   ├─ A1 StationAssemblyAgent  → 只读取证（ToolContext.allow_write=False，禁用 load_esop/bind_codes 写）
   ├─ B1 AssemblyEntryAgent    → 只读取证（同上，禁用 E-SOP 加载与履历写入）
   ├─ A3 QualityTraceAgent     → 只读分析
   ├─ B3 ControlCenterAgent    → 只读分析（主分析脑，未知编号回落）
   └─ B4 QualityTraceServiceAgent → 只读分析
```

- A2/A4/A5/B2/B5/C1–C3：第一版不进入主图路由（`resolve_codes` 过滤），代码保留但不被装配。
- 灰度 `rollout_mode` 默认 `shadow`：即使路由到上述 Agent，`ActionExecutor` 的写动作也被 `RolloutPolicy.allow_write=False` 拦截，仅生成方案不落库。
- 因此第一版的**实际执行边界**：全部为只读取证 + 方案生成，无任何自动写/控制；高风险动作走 `interrupt` 人工确认但默认不批准执行。

## 九、设计要点总结

1. **单一事实来源**：13 类智能体的路由/范围/只读/知识库对齐全部集中在 `agents/catalog.py`，`orchestrator` 不硬编码任何业务路由，改 catalog 即改行为。
2. **唯一装配点**：`graph/orchestrator.py` 是唯一 import 全部子系统并构造实例的地方，子系统之间零横向调用，保证流程确定、可回放、易测试。
3. **契约先行**：`models/*` 与 `tools/contracts.py` 是最底层零依赖契约，所有跨模块数据交换都走这些结构，杜绝隐式 dict 传递。
4. **风险三道闸**：① `ToolRegistry` 前置检查链（工具层拦截 write/control）；② `PlanValidator` 校验（方案层修正可执行标志）；③ `ActionExecutor.plan_dispatch` + 灰度策略（执行层三分桶）。三道闸独立且可分别审计。
5. **规则优先 + LLM 可选降级**：每个 specialist 先规则取证，`_llm_finding` 成功才覆盖，LLM 未配置或失败自动回落规则结果，系统在无 LLM 时仍可完整运行。
6. **人工确认安全默认**：`ConfirmStore` 超时置 `expired` 而非默认批准；`interrupt` 挂起图必须显式 `Command(resume)` 才继续，杜绝无人值守时的自动高风险执行。
