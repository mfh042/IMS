# 工业多智能体系统分阶段实施细化方案（可开发·可评审·可验收版）

> 底座：LangChain（能力）+ LangGraph（编排）+ 自研工业工具层（执行边界）+ 事件驱动接入 WMS / MES / QMS / EAM。
> 每个阶段统一按「目标 → 输入 → 处理逻辑 → 输出 → 数据结构 → 异常处理 → 验收标准」展开，并明确自动执行与人工确认边界。

---

> **本版完善说明**：本方案在原分阶段工程骨架基础上，融入《智能体构建清单方案》明确的
> “人工智能+制造”“人工智能+软件”两大框架下需构建的 13 类智能体（装备侧 A1–A5、软件侧 B1–B5、
> 行业专用 C1–C3），把原来抽象的“7 个通用 Agent”升级为与具体业务智能体逐一对齐的可落地规格，
> 并在各阶段补齐“本阶段服务于哪些智能体、智能体在此阶段如何落位”的映射。

## 建设目标：两大框架与 13 类智能体（贯穿全篇）

系统不改变现有主营业务，而是在两大框架下把现有装备与服务升级为“装备级大模型服务 + 装备级智能体服务”：

- **人工智能+制造**（装备侧）：让柔性装配平台、CTU 库房、AGV、智能/检测工位具备“感知—校验—执行—上报—记录”闭环，
  构建 **A1 工位装配、A2 物料配送、A3 质量追溯、A4 产线调度、A5 实训教学** 共 5 类装备侧智能体。
- **人工智能+软件**（软件侧）：把 MES/WMS/WCS/工位软件/追溯系统升级为可被智能调用的工业软件底座，
  构建 **B1 装配智能体入口、B2 物流智能体服务、B3 智能管控大模型服务、B4 质量追溯智能体服务、B5 实训智能体服务** 共 5 类。
- **行业专用**（两框架融合）：沉淀可复用行业工艺与追溯规则，构建 **C1 轨道装备装配、C2 航空装配、C3 快速换型** 共 3 类。

合计 13 类。下方各阶段在保留通用工程纪律的同时，标注与这 13 类智能体的对应关系。

# 阶段 0：场景定义与边界确认

## 0.1 目标
把"工业多智能体系统"从概念收敛为**可交付的有限场景**，避免一上来做全厂全场景。

## 0.2 输入
- 现有 WMS / MES / QMS / EAM 系统清单与接口文档
- 设备类型清单、报警代码表、SOP 文档、历史故障记录
- 现场角色：班组长、工艺员、质量员、设备工程师、计划员
- 现有权限体系（谁可以停机、谁可以冻结批次、谁可以改工单）

## 0.3 处理逻辑
1. 按「发生频率 × 影响程度 × 数据可得性 × 处置标准化程度」四维打分，选出 1–2 个试点场景。
2. 明确每个场景的**成功定义**：是缩短响应时间、减少误判、减少重复报警，还是提高工单填写质量。
3. 明确**红线清单**：哪些动作系统永远不自动执行。

## 0.4 输出
- 试点场景说明书（含业务现状、痛点、目标指标）
- 红线清单
- 角色与权限矩阵
- 数据可得性评估表

## 0.5 推荐试点优先级

| 优先级 | 场景 | 理由 |
|---|---|---|
| 高 | 设备异常诊断 + 维护建议 | 数据结构化好、SOP 明确、风险可控 |
| 中 | 质量批次不良追溯 | 价值高但依赖追溯链完整度 |
| 中 | 工单阻塞 + 缺料分析 | 依赖 WMS/MES 数据一致性 |
| 低 | 自动停机/参数调整 | 风险高，仅做建议 |

## 0.6 验收标准
- 至少 1 个场景具备：完整报警代码、可查设备状态、≥20 份可用 SOP/案例
- 红线清单经工艺、质量、设备、安全四方签字确认
- 明确 1 个可量化基线指标（如平均响应时长、误判率）


## 0.7 试点场景与智能体的映射

阶段 0 选定的试点场景，应直接收敛到 13 类智能体中的子集，避免“通用场景 + 抽象 Agent”两层脱节：

| 试点优先级 | 对应智能体（编号） | 主要框架 | 收敛理由 |
|---|---|---|---|
| 高（首批） | A3 质量追溯 + B4 质量追溯智能体服务 + B3 智能管控大模型服务 | 两框架协同 | 数据/追溯链结构化好、SOP 明确、只读为主、风险可控 |
| 中 | A2 物料配送 + B2 物流智能体服务 + A1 工位装配 + B1 装配智能体入口 | 两框架协同 | 依赖 WMS/MES 数据一致性与工单节拍 |
| 中 | A4 产线调度 | 制造侧 | 依赖工位/齐套/设备状态汇集 |
| 低（后续） | A5 实训教学 + B5 实训智能体服务 | 两框架 | 与生产异常闭环解耦，可独立排期 |
| 行业扩展 | C1/C2/C3 行业专用 | 两框架融合 | 通用底座稳定后，按行业模板复用上线 |

红线补充：凡智能体涉及停机复位、批次冻结、工单状态变更、参数修改（A1/A2/A3/A4 与 B2/B3/B4 均含此类动作），一律进入阶段 8 人工确认，不得自动执行。

# 阶段 1：事件接入与标准化

## 1.1 目标
把各系统异构事件统一为**标准事件模型**，保证后续所有智能体处理同一套输入。

## 1.2 输入
- WMS / MES / QMS / EAM 的推送或轮询数据
- 各系统字段字典、编码规则、时间戳时区

## 1.3 处理逻辑
1. **接入方式选择**：优先消息推送（Kafka / RabbitMQ / Redis Stream）；无消息能力的老系统用定时轮询 + 变更比对。
2. **字段映射**：把各系统字段映射到标准事件字段，映射表版本化管理。
3. **时间统一**：统一为带时区的 ISO8601，保留原始时间戳。
4. **标识生成**：生成 `event_id`（全局唯一）、`trace_id`（跨系统链路）、`idempotency_key`（幂等键）。
5. **缺失字段处理**：关键字段缺失时不丢弃，标记 `data_quality` 并降级处理。

## 1.4 标准事件结构

```python
from datetime import datetime
from typing import Literal
from pydantic import BaseModel, Field


class StandardEvent(BaseModel):
    event_id: str
    trace_id: str
    idempotency_key: str
    event_type: str
    source_system: Literal["WMS", "MES", "QMS", "EAM", "MANUAL"]
    occurred_at: datetime
    received_at: datetime | None = None
    severity: Literal["low", "medium", "high", "critical"]
    tenant_id: str
    factory_id: str | None = None
    line_id: str | None = None
    work_order_id: str | None = None
    material_id: str | None = None
    batch_id: str | None = None
    device_id: str | None = None
    alarm_code: str | None = None
    message: str | None = None
    payload: dict = Field(default_factory=dict)
    raw_payload: dict = Field(default_factory=dict)
    data_quality: Literal["complete", "partial", "suspicious"] = "complete"
    schema_version: str = "v1"
```

## 1.5 异常处理

| 异常 | 处理 |
|---|---|
| 字段缺失 | 标记 `partial`，仍进入流程，但限制高风险动作 |
| 格式非法 | 进入死信队列，通知接入负责人 |
| 时间戳异常（未来时间/大幅偏移） | 标记 `suspicious`，按接收时间处理并告警 |
| 重复事件 | 按 `idempotency_key` 丢弃或合并 |

## 1.6 验收标准
- 单一系统事件标准化成功率 ≥ 99%
- 死信队列有告警与人工兜底入口
- 任一事件可通过 `trace_id` 追溯到原始报文

# 阶段 2：事件治理（去重、聚合、限流、优先级）

## 2.1 目标
防止告警风暴，保证智能体处理的是**有意义的问题**而不是重复噪声。

## 2.2 输入
标准事件流

## 2.3 处理逻辑

**去重**：以 `idempotency_key` 为键，设定时间窗口（如 5 分钟）内重复事件只保留首条，其余计数累加。

**聚合**：按聚合键合并相关事件。

```text
聚合键 = 设备ID + 报警类型 + 时间窗口
或 = 工单ID + 工序 + 时间窗口
或 = 批次ID + 不良代码 + 时间窗口
```

聚合后生成 `incident`（问题实例），包含事件列表、首次时间、末次时间、次数、严重度取最大值。

**限流**：
- 全局并发上限（同时处理的 incident 数）
- 单设备/单工单限流
- 模型调用限流与预算控制
- 超限时进入排队或降级为规则处理

**优先级排序**：

```text
优先级分 = 严重度权重
         + 影响范围权重（停线/批量/在制数量）
         + 安全相关加权
         + 等待时长加权
```

## 2.4 输出结构

```python
class Incident(BaseModel):
    incident_id: str
    trace_id: str
    event_ids: list[str]
    event_count: int
    incident_type: Literal[
        "production_exception",
        "material_exception",
        "quality_exception",
        "equipment_exception",
        "mixed_exception"
    ]
    severity: Literal["low", "medium", "high", "critical"]
    priority_score: float
    first_occurred_at: datetime
    last_occurred_at: datetime
    entity_refs: dict
    status: Literal["new", "processing", "waiting_confirm", "closed", "failed"]
```

## 2.5 异常处理
- 聚合窗口内出现严重度升级 → 立即提升优先级并重新调度
- 限流触发 → 记录降级原因，低优先级事件延迟处理
- 治理层故障 → 事件不丢，落盘重放

## 2.6 验收标准
- 重复事件收敛率可统计（如原始事件数 / incident 数）
- 告警风暴场景下系统不崩溃、不丢事件
- 高优先级事件平均调度延迟有明确上限

# 阶段 3：数据与知识底座建设

## 3.1 目标
让智能体"查得到、查得准、查得有依据"。

## 3.2 输入
- 设备测点、报警、趋势、维保记录
- 工单、工序、在制品、报工
- 库存、批次、库位、发料
- 检验记录、不良代码、CAPA
- SOP、工艺规范、故障案例、设备说明书

## 3.3 处理逻辑

**结构化数据**：不搬迁业务库，通过只读视图/只读账号 + Adapter 查询，避免影响生产库。

**非结构化知识**：
1. 文档清洗（去页眉页脚、表格转结构化、图片另存）
2. 按语义分块（建议按"章节 + 步骤"切分，保留标题路径）
3. 每块绑定元数据：设备类型、适用报警、版本、生效日期、风险等级、责任人
4. 向量化 + 元数据双路检索（向量召回 + 元数据过滤）

**知识元数据结构**

```python
class KnowledgeChunk(BaseModel):
    chunk_id: str
    doc_id: str
    title: str
    section_path: str
    version: str
    effective_date: str
    expire_date: str | None = None
    applicable_device_types: list[str] = []
    applicable_alarm_codes: list[str] = []
    applicable_process: list[str] = []
    risk_level: Literal["low", "medium", "high"]
    owner: str
    text: str
    source_uri: str
```

**检索策略**：
- 召回：向量相似 + 关键词（报警代码、设备型号必须命中）
- 过滤：设备类型匹配、版本未过期、适用工序匹配
- 排序：匹配度 + 文档权威级 + 近期有效性
- 兜底：无命中时返回"无可靠依据"，禁止模型编造

## 3.4 输出
- 只读数据访问接口清单
- 知识库索引 + 元数据库
- 检索接口（返回带来源与版本的片段）

## 3.5 异常处理
- 文档过期 → 标记并降权，命中时提示"依据可能过期，建议人工确认"
- 元数据缺失 → 只允许作为参考，不允许支撑自动动作
- 数据源不可用 → 返回明确错误码，方案降级为"证据不足"

## 3.6 验收标准
- 抽样 30 个真实故障，知识检索命中率 ≥ 80%，且能给出来源与版本
- 无依据时能正确拒绝，而不是生成看似合理的方案
- 结构化查询不产生生产库写操作


## 3.7 四类工业知识库（支撑装备级大模型服务）

“人工智能+软件/制造”框架下，智能体效果取决于四类底座库的完整度，阶段 3 需逐库明确归属智能体：

| 知识库 | 内容 | 主要服务的智能体 | 元数据要求（沿用 KnowledgeChunk） |
|---|---|---|---|
| 工艺知识库 | 工艺文件、E-SOP、作业指导书、参数模板 | A1、B1、C1、C2、C3 | 工序、适用产品、版本、生效期、风险等级 |
| 质量规则库 | 不良代码、判定规则、CAPA、追溯规则 | A3、B4 | 不良代码、适用物料/产品、处置风险等级 |
| 设备参数库 | 设备型号、测点、阈值、维保与故障案例 | A1、A2、A4、B3（异常诊断） | 设备类型、报警代码、阈值、维护责任人 |
| 追溯数据 | 产品码—物料批次—工步—检测记录关联链 | A3、B4、B3（追溯分析）、C1/C2 | 产品码、批次、工步、检测结果、留痕时间 |

检索策略不变（双路召回 + 元数据过滤 + 无命中即拒绝），但需按智能体设置不同的必需元数据过滤维度：
装配类（A1/B1）必校验工序与版本；质量类（A3/B4）必校验不良代码与判定规则；设备类（B3 诊断）必校验报警代码与阈值。

# 阶段 4：工具层建设（统一受控入口）

## 4.1 目标
所有智能体通过**同一套受控工具**访问外部系统，实现权限、校验、审计、幂等、降级统一。

## 4.2 工具清单与风险等级

| 工具 | 类型 | 风险 | 自动执行 |
|---|---|---|---|
| 查询设备状态/报警/趋势 | 只读 | 低 | 是 |
| 查询工单/工序/在制 | 只读 | 低 | 是 |
| 查询库存/批次/库位 | 只读 | 低 | 是 |
| 查询检验/不良/追溯链 | 只读 | 低 | 是 |
| 知识检索 | 只读 | 低 | 是 |
| 记录诊断结果 | 写 | 低 | 是（审计） |
| 创建工单草稿 | 写 | 中 | 是（草稿态） |
| 发送通知/提示 | 写 | 中 | 是（审计） |
| 生成处置待确认单 | 写 | 中 | 是（待确认） |
| 停机/启机/改参数 | 控制 | 高 | 否 |
| 冻结批次/改工单状态 | 业务写 | 高 | 否 |

## 4.3 工具统一契约

```python
class ToolContext(BaseModel):
    trace_id: str
    incident_id: str | None = None
    actor: str
    roles: list[str]
    tenant_id: str
    allow_high_risk: bool = False


class ToolResult(BaseModel):
    ok: bool
    data: dict | list | None = None
    error_code: str | None = None
    error_message: str | None = None
    source: str
    fetched_at: datetime
    degraded: bool = False
```

## 4.4 工具执行前置检查（顺序固定）
1. 工具是否存在且已启用
2. 调用者角色是否有权限
3. 参数 schema 校验 + 业务校验（设备是否存在、时间范围是否合理）
4. 风险等级判断：高风险且 `allow_high_risk=False` → 直接拒绝并返回"需人工确认"
5. 幂等检查（写操作）
6. 超时与重试策略
7. 审计写入（调用前记录意图，调用后记录结果）

## 4.5 异常处理
- 超时 → 有限重试（只读可重试，写操作禁止盲目重试）
- 部分数据缺失 → 返回 `degraded=True`，方案必须标注证据不完整
- 权限不足 → 明确拒绝，不降级绕过
- 下游不可用 → 熔断 + 转人工

## 4.6 验收标准
- 任意工具调用都能通过 `trace_id` 还原调用参数与结果
- 高风险工具在无人工确认时 100% 被拦截（用测试用例验证）
- 写操作重复调用不产生重复业务数据


## 4.7 受控工具与 13 类智能体的对应关系

阶段 4 的统一工具按“装备侧感知执行 / 软件侧查询生成”分域，但全部经同一治理入口，避免各自直连设备：

| 工具域 | 代表工具 | 调用智能体 | 风险 | 自动执行 |
|---|---|---|---|---|
| 设备/工位状态查询 | 测点、在线、报警、扭矩检测数据 | A1、A3、A4、B3 | 低 | 是 |
| 工单/工序/在制查询 | 工单节拍、齐套、在制、报工 | A1、A2、A4、B2、B3 | 低 | 是 |
| 库存/批次/库位查询 | 可用量、批次状态、冻结标记 | A2、B2、B4 | 低 | 是 |
| 检验/不良/追溯链查询 | 检测记录、不良代码、追溯定位 | A3、B4、B3 | 低 | 是 |
| 知识检索 | 工艺/质量/设备/追溯四类库 | A1、A3、A4、B1、B3、B4、C1–C3 | 低 | 是 |
| E-SOP 加载与码绑 | 自动加载、绑定产品/物料/工具码、生成履历 | A1、B1 | 中（写） | 草稿/记录态可 |
| 工单草稿 / 通知 / 待确认单 | 缺料处置单、维护工单草稿、责任人通知 | A2、A3、A4、B2、B3、B4 | 中 | 待确认 |
| 停机复位 / 启机 / 改参数 | 设备控制类 | A1、A2、A4、B3 | 高 | 否（必人工确认） |
| 批次冻结 / 工单状态变更 | 业务写 | A2、A3、B2、B4 | 高 | 否（必人工确认） |
| 配送路径/调度调整 | 路径重算、动态调度下发 | A2、A4、B2 | 高 | 仅生成建议，确认后可执行 |

要点：装备侧 A1/A2/A4 与软件侧 B1/B2/B3/B4 共享同一套工具与契约（ToolContext/ToolResult），
不允许任一智能体绕过工具层直连设备或业务库写接口。

# 阶段 5：智能体设计与提示工程

## 5.1 目标
每个子 Agent 职责单一、输出结构化、可独立评测。

## 5.2 Agent 规格

| Agent | 输入 | 使用工具 | 输出 |
|---|---|---|---|
| 生产异常 | incident、工单、工序 | 工单/在制查询 | 影响范围、阻塞原因候选 |
| 物料库存 | 物料、批次、工单需求 | 库存/批次/库位 | 缺料判断、可用量、替代料 |
| 质量追溯 | 批次、不良代码 | 检验/追溯链 | 影响批次、上下游范围 |
| 设备诊断 | 设备、报警、趋势 | 设备状态/历史 | 故障假设、证据、置信度 |
| 维护建议 | 设备诊断 + 知识 | 知识检索 | 维护步骤、所需资源、风险 |
| 知识检索 | 关键词 + 元数据 | 知识检索 | 带来源版本的知识片段 |
| 控制建议 | 上述全部 | 无控制工具 | 控制建议 + 风险说明（不执行） |

## 5.3 统一输出结构

```python
class AgentFinding(BaseModel):
    agent_name: str
    summary: str
    findings: list[str]
    hypotheses: list[str] = []
    evidence: list[dict] = []
    knowledge_refs: list[str] = []
    confidence: float = Field(ge=0, le=1)
    data_gaps: list[str] = []
    suggested_next_steps: list[str] = []
    risk_notes: list[str] = []
```

## 5.4 提示词骨架（每个 Agent 通用）

```text
角色：你是{领域}分析助手，服务于工业现场{场景}。

输入：
- 事件与实体信息：{incident}
- 已查询数据：{tool_results}
- 知识依据：{knowledge_chunks}

要求：
1. 只基于给定数据与知识作答，不得编造设备状态、参数、文档内容。
2. 每条结论必须给出对应证据来源；证据不足时明确写入 data_gaps。
3. 区分"事实"与"假设"，假设必须标注置信度。
4. 不输出任何直接控制设备的指令；如需控制，仅输出建议与风险。
5. 严格按给定 JSON 结构输出，不添加额外字段。

输出：AgentFinding 结构
```

## 5.5 结构化输出与校验
- 使用结构化输出 + Pydantic 校验
- 校验失败 → 一次修复重试 → 仍失败则标记该 Agent 失败，主调度按"证据不足"处理
- 禁止让校验失败的结果进入方案生成

## 5.6 异常处理
- 工具全部失败 → 返回低置信 + 数据缺口，不生成方案
- 知识无命中 → 明确"无标准依据"，建议人工判断
- 多 Agent 结论冲突 → 主调度保留冲突并降置信，不强行统一

## 5.7 验收标准
- 每个 Agent 有 ≥20 条评测样本，输出结构合规率 ≥ 95%
- 编造检测：无数据时不得输出具体数值/文档内容
- 单 Agent 可独立重跑并得到可比较结果

# 阶段 6：主调度与 LangGraph 编排

## 6.1 目标
用确定性图结构编排智能体，保证流程可预测、可回放、可人工介入。

## 6.2 图设计

```text
START
 → normalize_event
 → governance_check
 → classify_incident
 → plan_subtasks
 → run_specialists（可并行）
 → retrieve_knowledge
 → merge_findings
 → build_resolution_plan
 → validate_plan
 → risk_route
     ├─ execute_safe_actions
     ├─ execute_medium_risk_actions
     └─ request_human_confirm（中断点）
 → record_result
 → respond
 → END
```

## 6.3 关键节点规格

**classify_incident**：规则优先（报警代码/事件类型映射），模型仅处理模糊情况；输出 `incident_type` 与置信度。

**plan_subtasks**：按类型映射子 Agent 组合，例如设备异常 → 设备诊断 + 维护建议 + 知识检索；混合异常 → 多 Agent + 交叉校验。

**run_specialists**：并行执行，设置单 Agent 超时；失败不阻塞整体，但记录数据缺口。

**merge_findings**：
- 去重证据
- 标注冲突（如设备诊断说散热问题，质量追溯说参数异常）
- 计算综合置信度（取保守值，而非平均）

**validate_plan**：校验方案完整性、证据是否支撑结论、知识是否适用、是否包含未授权动作。

## 6.4 状态定义

```python
class IndustrialAgentState(TypedDict, total=False):
    event: dict
    incident: dict
    incident_type: str
    subtasks: list[dict]
    agent_findings: dict
    knowledge_refs: list[dict]
    merged_findings: dict
    resolution_plan: dict
    risk_level: str
    need_human_confirm: bool
    confirm_request: dict
    confirm_status: str
    executed_actions: list[dict]
    final_answer: str
    audit_log_id: str
    errors: list[dict]
```

## 6.5 人工确认节点
- 使用图的中断机制暂停，等待外部确认
- 确认请求必须包含：动作、参数、风险、回滚方式、责任人、超时策略
- 恢复执行时重新校验权限与参数（不信任中断前的状态）

## 6.6 异常处理
- 节点异常 → 记录并走"降级响应"：给出已知信息 + 明确不确定项 + 转人工
- 全局超时 → 输出部分结论并标记未完成
- 重复触发 → 幂等键保证不重复执行动作

## 6.7 验收标准
- 全流程可从 `trace_id` 回放每个节点输入输出
- 人工确认能正确暂停与恢复
- 任一节点失败都不会导致高风险动作被执行


## 6.8 13 类智能体的子图编排映射

主调度按“框架域 → 子图 → 具体智能体”三级编排，装备侧为“感知—执行—上报”子图、软件侧为“调用—分析—生成”子图：

| 事件来源 | 触发的主调度路由 | 调用的智能体子图 |
|---|---|---|
| 设备/工位报警 | equipment_exception | 设备诊断（B3）→ A1/A3 取证 → C1/C2 行业规则（如适用） |
| 工单阻塞 / 缺料 | mixed：production+material | A2 物料配送 + B2 物流 + A4 产线调度 + A1 工位状态 |
| 质量不良 / CAPA | quality_exception | A3 质量追溯 + B4 追溯服务 + B3 根因辅助 |
| 装配履历/工艺问答 | query（MANUAL 或 A1 上报） | B1 装配入口 + A1 + 工艺知识库 |
| 实训任务 | 独立链路（不入异常主链） | A5 + B5 |

约束：
- 装备侧子图与软件侧子图通过统一工具层与 `IndustrialAgentState` 显式传参，禁止子图间隐式共享或各自直连设备。
- 行业专用 C1–C3 以“规则/模板增强”方式注入对应通用子图，而非新增自由协作 Agent。
- `plan_subtasks` 节点按 5.8 编号决定调用哪些子图，`run_specialists` 内对同域子图可并行。

# 阶段 7：方案生成与风险分级

## 7.1 目标
把多 Agent 结论转化为**可执行、可审计、可分级**的解决方案。

## 7.2 方案结构

```python
class ProposedAction(BaseModel):
    action_id: str
    action_type: Literal[
        "query_only", "notify_user", "create_ticket_draft",
        "execute_safe_function", "request_human_confirm", "control_suggestion"
    ]
    title: str
    description: str
    risk_level: Literal["low", "medium", "high"]
    requires_human_confirm: bool
    executable: bool
    tool_name: str | None = None
    tool_args: dict | None = None
    preconditions: list[str] = []
    rollback_hint: str | None = None
    evidence_refs: list[str] = []


class ResolutionPlan(BaseModel):
    plan_id: str
    incident_id: str
    problem_summary: str
    root_cause_hypotheses: list[dict]
    evidence: list[dict]
    knowledge_references: list[dict]
    actions: list[ProposedAction]
    user_instruction: str | None = None
    prohibitions: list[str] = []
    data_gaps: list[str] = []
    need_human_confirm: bool
    confidence: float
    validity_note: str | None = None
```

## 7.3 风险分级规则（规则优先，模型辅助）

| 判定条件 | 风险 |
|---|---|
| 仅查询、仅提示 | 低 |
| 生成草稿、发送通知、记录诊断 | 中 |
| 涉及设备启停、参数修改、批次冻结、工单状态变更、安全相关 | 高 |
| 证据不完整 / 知识过期 / 多 Agent 冲突 | 至少升一级 |
| 数据质量 `partial` 或 `suspicious` | 至少升一级 |

## 7.4 方案校验清单
- 每条结论是否有证据引用
- 每个动作是否有前置条件与回滚提示
- 是否存在无依据的动作
- 是否包含被禁止的动作类型
- 置信度是否与证据强度匹配
- 是否明确标注数据缺口与不确定项
- 是否给出人工确认的触发原因
- 是否对高风险动作给出责任人建议与超时策略
- 是否避免输出具体控制指令（仅输出建议与风险）

校验不通过的处理：

| 校验失败项 | 处理 |
|---|---|
| 结论无证据 | 删除该结论，或降级为"待验证假设" |
| 动作无前置条件 | 补齐前置条件，无法补齐则置 `executable=false` |
| 出现禁止动作 | 直接拦截，记录审计，转人工 |
| 置信度与证据不匹配 | 下调置信度，并升级风险等级 |
| 知识过期 | 保留引用但标注"依据可能过期"，禁止自动执行 |

## 7.5 置信度计算（保守策略）

```text
综合置信度 = min(
    各相关 Agent 置信度,
    证据完整度评分,
    知识适用性评分
)

证据完整度 = 已获取关键数据项 / 该场景必需数据项
知识适用性 = 命中且未过期且设备/工序匹配 的文档权重
```

不使用平均值，避免"一个强证据掩盖多个缺口"。

# 阶段 8：执行与人工确认闭环

## 8.1 目标
让低风险动作真正闭环，中风险动作形成待办，高风险动作受控确认，全过程可回滚。

## 8.2 执行分流

| 风险 | 执行方式 | 典型动作 |
|---|---|---|
| 低 | 自动执行 | 补充查询、记录诊断结果 |
| 中 | 自动执行但生成待办 | 工单草稿、通知责任人、处置建议单 |
| 高 | 生成确认请求，人工审批后执行 | 停机、改参数、冻结批次、改工单状态 |

## 8.3 执行前置再校验（不可跳过）
1. 权限再校验（以当前操作者为准，不沿用生成方案时的角色）
2. 参数再校验（重新查设备/工单/批次当前状态）
3. 幂等再校验（同一 `incident_id + action_id` 只执行一次）
4. 前置条件再校验（如"设备处于运行态"是否仍成立）
5. 审计写入执行意图

任一不通过 → 不执行，转为"需人工处理"并说明原因。

## 8.4 人工确认请求结构

```python
class ConfirmRequest(BaseModel):
    confirm_id: str
    incident_id: str
    plan_id: str
    action_id: str
    action_title: str
    action_detail: str
    tool_name: str
    tool_args: dict
    risk_level: str
    risks: list[str]
    rollback_hint: str
    required_roles: list[str]
    assignee: str | None = None
    created_at: datetime
    expire_at: datetime
    status: Literal["pending", "approved", "rejected", "expired", "executed", "failed"]
    decision_by: str | None = None
    decision_at: datetime | None = None
    decision_note: str | None = None
```

## 8.5 确认超时策略
- 超时未确认 → 状态置 `expired`，不自动执行
- 通知升级（责任人 → 上级）
- 记录为"未处置"，进入待办看板
- 严禁"超时默认同意"

## 8.6 执行结果记录

class ActionExecution(BaseModel):
    execution_id: str
    incident_id: str
    plan_id: str
    action_id: str

## 8.7 回滚设计
- 每个可执行动作在生成时必须给出回滚方式，无法回滚的动作不得自动执行
- 回滚同样走权限校验 + 审计
- 回滚失败 → 立即升级人工，标记事件为"需紧急处理"

## 8.8 异常处理

| 异常 | 处理 |
|---|---|
| 执行失败 | 记录错误码，尝试一次安全重试（仅幂等且只读/可重复写） |
| 部分成功 | 标记 `partial`，列出已完成与未完成项，转人工 |
| 状态已变化 | 中止执行，重新分析或转人工 |
| 确认人权限不足 | 拒绝并重新指派 |

## 8.9 验收标准
- 高风险动作无确认记录时执行次数为 0
- 确认超时不会自动执行
- 每个已执行动作都有执行记录与回滚提示
- 重复触发同一事件不产生重复工单/重复通知

# 阶段 9：审计、可观测与评估

## 9.1 目标
让系统"能被审查、能被复盘、能被持续改进"。

## 9.2 审计记录内容

```python
class AuditRecord(BaseModel):
    audit_id: str
    trace_id: str
    incident_id: str | None
    actor: str
    roles: list[str]
    action: str
    target: str | None
    input_snapshot: dict
    output_snapshot: dict
    risk_level: str | None
    decision: Literal["allowed", "denied", "confirmed", "rejected", "executed", "rolled_back"]
    reason: str | None
    created_at: datetime
```

审计必须覆盖：事件接入、治理决策、Agent 调用、工具调用、知识命中、方案生成、风险判定、确认审批、执行与回滚。

## 9.3 可观测指标

| 类别 | 指标 |
|---|---|
| 事件 | 事件量、重复率、聚合率、死信量 |
| 时延 | 事件到方案生成时长、到执行时长 |
| 智能体 | 各 Agent 成功率、结构合规率、平均置信度 |
| 检索 | 知识命中率、过期命中率、无命中转人工率 |
| 执行 | 自动执行数、确认数、拒绝数、失败率、回滚率 |
| 质量 | 误判率、漏判率、人工推翻率 |
| 成本 | 单事件模型调用次数与开销 |

## 9.4 评估集建设
- 从历史事件中抽取 100–300 条，按场景分层
- 每条标注：正确问题判定、正确原因、正确处置、应否人工确认
- 分为开发集、验证集、保留测试集，避免调参污染

## 9.5 评估方式
- 判定类：准确率、召回率、误报率
- 方案类：证据支撑率、动作合规率、人工采纳率
- 安全类：高风险动作违规执行次数（目标恒为 0）
- 回归机制：每次改提示词、改工具、改模型，跑完整评估集

## 9.6 验收标准
- 任一历史事件可完整回放：事件 → 治理 → Agent → 知识 → 方案 → 执行
- 关键指标有基线与目标值，且可按月对比
- 高风险违规执行次数为 0

# 阶段 10：集成与上线

## 10.1 目标
在不影响现有业务系统的前提下，逐步接入并放量。

## 10.2 集成方式

| 方式 | 适用 | 说明 |
|---|---|---|
| 消息订阅 | 有消息能力的系统 | 首选，低侵入 |
| 只读视图/只读账号 | 数据库直连场景 | 严禁写权限 |
| API 适配 | 有开放接口的系统 | 统一走 Adapter |
| 定时轮询 | 老旧系统 | 需做变更比对与去重 |
| 人工录入 | 无系统记录的场景 | 作为补充事件源 |

## 10.3 上线阶段

**阶段 A：影子模式（只读）**
- 系统接收事件、生成方案，但不执行任何写操作
- 与人工实际处置结果对比，统计误判与漏判

**阶段 B：低风险自动**
- 开放查询、记录诊断、生成工单草稿、发送通知
- 保留全量审计与人工抽查

**阶段 C：中风险闭环**
- 待办确认流上线，责任人处理闭环
- 统计采纳率与推翻率

**阶段 D：高风险受控**
- 仅对少数明确、可回滚、有权限约束的动作开放审批后执行
- 每次执行强制双人确认或上级确认（按现场制度）

## 10.4 灰度与回退
- 按产线 / 设备类型 / 事件类型灰度
- 提供总开关：一键停止自动执行，退回纯提示模式
- 提供场景开关：单场景可独立停用
- 模型或知识异常时自动降级为规则 + 人工

## 10.5 验收标准
- 影子模式期间不影响任何业务系统写入
- 灰度期间业务系统无因本系统导致的故障
- 回退开关在分钟内生效并验证过

# 阶段 11：运维、迭代与治理

## 11.1 日常运维
- 死信队列每日清理与归因
- 知识库版本与生效期巡检
- 工具接口可用性与超时监控
- 模型成本与调用量监控
- 确认待办积压监控

## 11.2 知识治理
- 文档变更触发重新索引
- 过期文档自动降权并提示
- 人工推翻的结论回流为案例，经审核后入库
- 知识责任人制度，避免"无人维护的 SOP"

## 11.3 提示词与模型迭代
- 提示词版本化管理，变更需过评估集
- 模型更换需做同集对比，不直接上线
- 保留旧版本可快速回退

## 11.4 治理机制
- 建立变更评审：新增工具、新增可执行动作、调整风险规则必须评审
- 建立红线清单年度复核
- 建立事件复盘机制：误判、漏判、违规拦截均复盘

## 11.5 验收标准
- 知识过期率、待办积压率、死信量有明确阈值与告警
- 提示词/模型/工具变更均有评估记录
- 每季度输出一次误判率与采纳率报告

# 阶段 12：第一版最小可用范围（建议）

## 12.1 只做一件事
**设备异常诊断 + 维护建议 + 工单草稿**，其余场景后续扩展。

## 12.2 第一版包含
- 单一设备系统事件接入
- 事件标准化 + 去重 + 聚合
- 设备诊断 Agent + 维护建议 Agent + 知识检索 Agent
- 主调度 LangGraph 流程
- 只读工具 + 工单草稿 + 通知
- 风险分级与人工确认（仅确认，不执行控制）
- 审计与回放
- 评估集 ≥ 50 条

## 12.3 第一版明确不做
- 不执行停机、启机、参数修改
- 不修改工单状态、不冻结批次
- 不做多产线全场景
- 不做自由协作的多智能体
- 不做无人工确认的写操作

## 12.4 第一版成功标准
- 事件到方案生成时延满足现场要求
- 诊断结论人工采纳率达到约定阈值
- 高风险违规执行次数为 0
- 全链路可回放


## 12.5 第一版收敛到哪些智能体

把 12.1 的“设备异常诊断 + 维护建议 + 工单草稿”落到 5.8 编号上，第一版只做：

- **B3 智能管控大模型服务**（异常诊断、维护建议、报表生成的主入口）
- **A3 质量追溯智能体 + B4 质量追溯智能体服务**（取证与追溯定位）
- 关联调用 **A1 工位装配 / B1 装配入口** 只读取证（不触发其写动作）

第一版明确不做（对应 5.8 边界）：A2/B2 配送路径下发、A4/B3 停机启机改参数、批次冻结与工单状态变更，
以及 C1–C3 行业专用与 A5/B5 实训类。所有上述高风险动作按阶段 8 仅生成建议与待确认，不执行。
